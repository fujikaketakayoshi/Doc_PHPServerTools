## 2. 対応環境と採用技術

### PHP

- [x] 最低PHPバージョンは8.3とする
-- [!] XServerは現在PHP 8.3を選択できるため、最初の動作確認環境として問題ない。古いPHPへ対応するための分岐は作らない。[XServerのPHP仕様](https://www.xserver.ne.jp/manual/man_program_soft.php)

インストーラーで次の拡張・機能を検査する。

| 種別 | 拡張・機能 | 用途 |
|---|---|---|
| 必須 | `pdo_sqlite` または `sqlite3` | SQLite接続 |
| 必須 | `mbstring` | 日本語の文字数・エンコーディング処理 |
| 必須 | `dom` | PDF用HTMLの処理 |
| 必須 | `session`、`filter`、`hash` | 認証、入力検証、トークンのハッシュ化 |
| 必須 | `fileinfo` | バックアップのファイル検査 |
| 推奨 | `zip` | バックアップZIPの作成・復元 |
| 推奨 | `zlib` | 圧縮 |
| 任意 | `gd` | QRをPNG出力する場合。SVGだけなら不要 |

`json`、`random_bytes()`、パスワードAPIはPHP 8.3の標準機能として利用する。`zip` がない環境への代替形式を作って対応範囲を広げるより、初期版では必須へ格上げすることもXServer実機の環境診断後に判断する。

### QRコードとPDF

- [x] QR生成は `endroid/qr-code` のPHP 8.3対応版を固定して使う
-- [!] 同ライブラリはSVG、PNG等を生成できる。最新版を無条件追従せず、PHP 8.3で動作するメジャーバージョンをComposerのロックファイルで固定する。SVGを標準にすればGDなしでも印刷品質を保ちやすい。[endroid/qr-code](https://github.com/endroid/qr-code)
- [x] PDF生成は `dompdf/dompdf` を使用し、日本語フォントを配布物へ同梱する
-- [!] Dompdfは外部フォントをPDFへ埋め込める。標準同梱のDejaVuだけに頼らず、ライセンスを確認したNoto Sans JP等の日本語TrueTypeフォントを同梱し、CSSの `@font-face` で指定する。イベント名とスポット名を含む実PDFをテストし、文字化けと改行を確認する。[Dompdfのフォント仕様](https://github.com/dompdf/dompdf#about-fonts--character-encoding)
-- [!] Dompdfは日本語の禁則処理が完全ではないため、MVPのPDFでは長文を載せず、イベント名、スポット名、短い案内文だけにする。長い説明は印刷用HTMLへ任せる。

### データベース

- [x] MVPはSQLiteを採用する
-- [!] XServerはSQLiteを公式に利用可能としている。ロリポップ、さくらのレンタルサーバ、ヘテムルでも公式仕様上の対応を確認できたため、XServer固有の選択にはなりにくい。[XServer](https://www.xserver.ne.jp/manual/man_db_spec.php) / [ロリポップ](https://lolipop.jp/service/server-spec/) / [さくら](https://help.sakura.ad.jp/rs/2251/) / [ヘテムル](https://secure.heteml.jp/service/function/)
-- [!] SQLiteなら利用者によるDB作成、ホスト名・ユーザー名・パスワード入力が不要になり、ZIP設置型ツールの導入手順とバックアップが大幅に簡単になる。想定規模も20スポット、2,000人、最大40,000取得履歴なので、総データ量だけを理由にMySQLを選ぶ必要はない。
-- [!] 一方でSQLiteは書き込みを同時に1件ずつ処理する。WALモード、短いトランザクション、`busy_timeout`、一意制約違反時の適切な処理を使用し、XServer上の集中アクセス試験を採用条件とする。試験で現実的な待ち時間やエラー率を満たせない場合だけMySQLへ再検討する。MVPでSQLiteとMySQLの両対応はしない。

### 最初の動作確認環境

- [x] XServerのスタンダードプランを最初の動作確認・設置手順の対象とする
-- [!] XServerのサーバー仕様はSQLite、PHP 8.3、Cron、SSH、`mod_rewrite`、`.htaccess` を利用可能としている。サーバー世代による差があるため、契約した実サーバーでインストーラーの環境診断結果を保存する。[XServerサーバー仕様](https://www.xserver.ne.jp/manual/man_server_spec.php)

### 直下・サブディレクトリ設置

- [x] ドメイン直下とサブディレクトリ設置の両方へ対応する
-- [!] XServer自身も初期ドメインのサブディレクトリをテストサイト用途として案内しているため、サブディレクトリ設置は特殊な使い方ではない。[XServerのテストサイト例](https://www.xserver.ne.jp/bizhp/test-site/)
-- [!] URLを `/` 始まりで直書きせず、インストール時に保存したベースURLから生成する。例は `https://example.com/`、`https://server-id.xsrv.jp/qr-rally/`、`http://192.168.11.5/`。これで本番とローカルの両方を同じコードで扱える。ローカルではApacheの80番ポートを使うためポート番号を省略し、サブディレクトリ配置時だけURLへそのパスを加える。
-- [!] Macの `/etc/hosts` を変更しても、その設定はMac自身にしか効かず、スマートフォンは同じ名前を解決できない。スマートフォン実機テストではMacのLAN内IPアドレスを使うか、ルーター・ローカルDNS・mDNSへ名前を登録する。
-- [!] PHPから `ipconfig getifaddr en0` を実行してURLを自動決定しない。Wi-Fi以外、有線、VPN、複数NIC、コマンド実行禁止環境で誤判定するため。開発用のベースURLを設定ファイルまたは環境変数で明示する。Mac上のApacheをLAN内からアクセス可能な設定にし、同一LANのスマートフォンから `http://192.168.11.5/` または実際のサブディレクトリURLへアクセスする。

### 実行環境の切り替え

- [x] `development` と `production` を設定で切り替える
-- [!] 環境名だけで処理を大きく分けず、デバッグ表示、ログレベル、ベースURL、Cookieの `Secure`、テストデータ機能を設定値として切り替える。本番では詳細エラーとテストデータ投入を必ず無効にする。

これらの確定事項は [共通基盤・配布運営TODO](../todos/common-platform.md) にも反映する。

## 3. アプリケーション構成

- フレームワークへ依存しないPHPアプリケーション
- データベースはSQLiteのみ
- HTMLはサーバー側で生成し、JavaScriptは画面補助と復元の分割処理に限定
- CSSとアイコン等は配布物へ同梱し、外部CDNを使わない
- 参加者画面と管理画面を同じアプリ内で分離
- 1インストールにつき管理者1人、イベント1件
- URL生成時は設定済みのベースURLを使用し、ドメインをDBデータへ不用意に埋め込まない

SQLite接続時は少なくとも次を行う。

- DBファイルを公開ディレクトリ外へ保存する
- 接続ごとに外部キー制約を有効化する
- WALモードを有効化する
- `busy_timeout=5000ms` を設定する
- スタンプ取得等の書き込みトランザクションを短く保つ
- `database is locked` は100ms待機後と250ms待機後の最大2回だけ再試行する。回数・待機時間を差し替えてテストできる構造にする
- 再試行後もロックを取得できない場合はHTTP 503と「アクセスが集中しています。少し時間をおいて、もう一度QRコードを読み取ってください。」という趣旨の案内を返す
- 一意制約違反はSQLiteロックとして再試行せず、従来どおり取得済みとして扱う
- タイムアウト後の同じQRの再読み取りは安全に処理し、直前の処理が成功していた場合も `participant_id` と `spot_id` の一意制約で重複取得を防ぐ
- 起動時または診断画面で、DBディレクトリの書込権限とロック動作を実際に確認する

推奨する領域分割は次のとおり。

- `public`: Webから直接参照する入口、CSS、JavaScript、標準画像
- `bin`: ローカルセットアップ、マイグレーション、緊急認証再設定等のCLI専用コマンド
- `src`: 画面処理、業務処理、DB処理、入力検証
- `templates`: HTMLテンプレート
- `config`: 実行環境、ベースURL、DBファイルの場所等の設定。可能なら公開ディレクトリ外
- `storage`: SQLite DB、一時バックアップ、エラーログ。Webから直接取得不可
- `database`: 初期スキーマとマイグレーション
- `tests`: 自動テスト
-- [!] XServerでは `対象ドメイン/public_html` がドキュメントルートになる。可能なら公開ファイルを `public_html/qr-rally/`、DB・設定・ログを `対象ドメイン/qr-rally-private/` に置く。公開領域外へ置けない環境では、アプリ配下の保護ディレクトリへ置き、`.htaccess` と直接アクセス試験で遮断する。[XServerの初期フォルダ](https://www.xserver.ne.jp/manual/man_server_folder.php)

## 5. データモデル

テーブル名は実装時に接頭辞を付けられるようにする。主キーは内部用の数値IDとし、URLやCookieへ内部IDを出さない。

### `admins`

- `id`
- `email`（一意）
- `password_hash`
- `recovery_key_hash`
- `auth_version`（認証情報の再設定時に加算）
- `last_login_at`
- `created_at`、`updated_at`

管理者セッションへログイン時点の `auth_version` を保存し、各管理画面リクエストでDB上の値と一致することを確認する。パスワード、復旧キー、緊急CLIのいずれかで認証情報を変更した場合は `auth_version` を加算し、発行済みセッションをすべて無効化する。

### `app_settings`

- `setting_key`（一意）
- `setting_value`
- `updated_at`

製品バージョン、スキーマバージョン、ベースURL、メンテナンス状態等を保持する。秘密情報を何でも入れる汎用箱にはしない。

### `events`

MVPでは常に最大1件だけ保持する。

- `id`
- `name`
- `description`
- `notice_text`
- `starts_at`、`ends_at`
- `is_paused`、`pause_message`
- `required_stamp_count`
- `completion_message`
- `application_enabled`
- `application_deadline_at`
- `privacy_purpose_text`
- `created_at`、`updated_at`

開催状態は保存せず、現在日時、開催期間、`is_paused` から算出する。

`privacy_purpose_text` の初期値は「抽選と当選者への連絡のために使用します。」とする。これは固定文ではなく、管理者が応募設定画面で運用内容に合わせて変更できる。

### `application_fields`

- `id`
- `field_type`（`name`、`email`、`address`、`phone`）
- `is_enabled`
- `is_required`
- `display_order`

### `spots`

- `id`
- `public_token_hash`（一意）
- `name`
- `description`
- `display_order`
- `is_active`
- `created_at`、`updated_at`

QRへは平文のUUID v4を含め、DBへはそのハッシュだけを保存する。QR再発行時はトークンを変更できるようにする。

### 個別QRのSVGファイル名

個別SVGのダウンロード名は次の形式とする。

```text
表示順-日本語スポット名-qr.svg
```

例:

- `01-中央図書館-qr.svg`
- `02-市役所受付-qr.svg`

生成規則は次のとおり。

- 表示順はダウンロード時点の `display_order` を2桁でゼロ埋めする
- スポットを並び替えて再ダウンロードした場合は新しい表示順を使う
- 日本語スポット名はASCIIへ変換せず維持する
- `\\`、`/`、`:`、`*`、`?`、`"`、`<`、`>`、`|` と制御文字を `-` へ置換する
- 置換で連続した `-` は1個へまとめ、前後の空白、ピリオド、`-` を除去する
- 置換後のスポット名が空なら `spot` を使用する
- 長すぎる名前は拡張子を含むヘッダー長を考慮して安全な長さに切り詰める

HTTPレスポンスは `Content-Type: image/svg+xml; charset=UTF-8` と `X-Content-Type-Options: nosniff` を指定する。`Content-Disposition` はRFC 5987形式のUTF-8名とASCII代替名を併記する。

```text
Content-Disposition: attachment; filename="spot-01-qr.svg"; filename*=UTF-8''01-%E4%B8%AD%E5%A4%AE%E5%9B%B3%E6%9B%B8%E9%A4%A8-qr.svg
```

ヘッダー値へ改行を混入させない。日本語名とASCII代替名の両方を自動テストする。

### QRコードの再発行

再発行は、URLの漏えい、意図しない共有、誤掲示等により、現在のQRを明示的に無効化したい場合に使用する。

- 新しいUUID v4を生成し、そのハッシュで `public_token_hash` を置き換える
- 古いQR URLは更新完了直後から無効とし、通常の存在しない・無効なQR画面を返す
- スポット名、説明、表示順、停止状態、過去の取得実績は変更しない
- 再発行操作はPOST、管理者認証、CSRF検証を必須とする
- 操作ログへスポットID、成功・失敗、実行日時を記録し、旧・新トークンは記録しない

QR確認画面へ次の趣旨の注意を常時表示する。

> 再発行すると古いQRコードは使えなくなります。印刷・掲示・配布済みのQRコードは、すべて新しいものへ交換してください。

再発行ボタンを押した際の最終確認ダイアログにも、古いQRが無効になることと、印刷・掲示・配布済みQRの交換が必要になることを明記する。確認文の入力やチェックボックスは要求しない。

### QR印刷物

管理画面のメニュー、ページ見出し、関連する画面名と操作手順では、スポットの管理機能を「スポット管理」と表記する。

スポット取得URLはQRと同じくスタンプ取得に使用できる情報であるため、次の印刷物には平文で表示しない。取得用QRコード自体は従来どおり表示する。

- スポット個別印刷画面
- 全スポット印刷画面
- 全スポットPDF

これはQR画像の撮影や共有を完全に防止するものではないが、平文URLのコピーや手入力による不要な共有を抑えるための措置とする。広く案内するイベント入口URLはイベント入口用印刷画面へ平文でも表示する。管理者向けQR確認画面の表示内容は変更しない。

スポット個別印刷と全スポットPDFは、各スポットにつきA4一枚へ収める。イベント名とスポット名を固定幅からはみ出さず折り返し、スポット名・注意書き・QRコードを重ねない。特にPDF上部のイベント名は、長い日本語名でも左右が欠けないよう表示幅と改行位置を明示的に調整する。

イベント入口用印刷画面は、イベント説明や参加者向け注意事項の内容量に応じて複数ページになることを許容する。A4一枚へ収めるために文章を切り捨てたり表示領域から隠したりせず、次ページへ自然に続ける。

### `participants`

- `id`
- `token_hash`（一意）
- `nickname`
- `first_seen_at`、`last_seen_at`
- `completed_at`
- `created_at`、`updated_at`

Cookieへ平文のUUID v4、DBへハッシュを保存する。平文トークンをログへ残さない。

### QRコード読み取り時のブラウザに関する注意

参加情報とスタンプ履歴は、参加者が使用するブラウザのCookieで識別する。現在の方式を維持し、参加者向け復旧キーはMVPへ導入しない。Cookie削除、機種変更、別ブラウザの使用、コードスキャナーの利用によって履歴を失った場合、MVPでは履歴を復旧・統合できない。

#### iPhoneでの実機検証結果

iPhone SE（第3世代、iOSバージョン未記録）で、有効期限付きCookieを使いA用・B用のQRを別々に読み取った。

- コントロールセンターの「コードスキャナー」では、Aの画面内で通常リンクからBへ移動するとCookieが維持された
- Aの画面を閉じ、コードスキャナーでBのQRを別途読み取るとCookieは送信されなかった
- 標準の「カメラ」アプリでAをSafariから開いた後、Bを別途読み取った場合はCookieが維持された

コードスキャナーは同じ画面内だけ一時的にCookieを維持する。このため、初回参加フォームの前でCookieを確認しても、画面を閉じた後の保持可否は判定できない。コードスキャナーを技術的に確実に判別する方法には依存せず、参加者への明示的な案内で対応する。

#### 参加者への表示

初回参加フォームの直前へ、次の警告を他の説明から独立した目立つ枠として常時表示する。

> iPhoneをご利用の方へ<br>
> コントロールセンターの「コードスキャナー」で開いている場合は、この画面を閉じてください。<br>
> 標準の「カメラ」アプリでQRコードを読み直し、Safariから参加してください。コードスキャナーでは、画面を閉じると参加履歴やスタンプが引き継がれません。

参加者へ次を案内する。

- QRコードを端末の標準カメラで読み取り、普段使用している通常ブラウザで開く
- イベント中は毎回同じブラウザを使用する
- iPhoneでは標準の「カメラ」アプリから読み取り、Safariで開く
- iPhoneのコントロールセンターにある「コードスキャナー」は、画面を閉じると次回のQR読み取りへCookieが引き継がれないため使用しない
- Androidでは標準カメラから読み取り、Chrome等の普段使用しているブラウザで開く
- アプリ内ブラウザ、一時的なブラウザ、プライベートブラウズでは、画面を閉じた際にCookieと参加履歴が失われる場合がある

同じ趣旨の案内を次の場所へ掲載する。媒体に応じて文章量は短縮してよいが、標準カメラ、同じ通常ブラウザ、履歴消失の可能性を省略しない。

1. 初回参加フォーム直前の警告枠
2. 参加者向け諸注意画面
3. 各スポットのQR掲示物
4. イベント入口用案内
5. 参加者向け取扱説明書

諸注意画面は参加後もスタンプ一覧等から開けるようにする。Androidでは標準カメラからChrome等の普段使用する通常ブラウザで開き、イベント中は毎回同じブラウザを使うよう案内する。

#### 開発用Cookie検証ツール

実装リポジトリの `tools/cookie-probe/` に、iPhoneのCookie保持を確認する開発専用ツールを置く。有効期限付きCookieとセッションCookie、A用・B用の別QRを使い、PHPが実際に受信したCookieを基準として「同じCookieを確認」「Cookieなし」「別の検証ID」を判定する。検証結果記録用Markdownも同梱する。

このツールはGitで管理するが、本番配布ZIPには含めない。

### `stamp_acquisitions`

- `id`
- `participant_id`
- `spot_id`
- `acquired_at`
- `ip_hash`（乱用調査用。アプリ秘密鍵を使ったHMAC-SHA256識別値）

`participant_id` と `spot_id` の組を一意制約にし、同時リクエストでも重複取得を防ぐ。

### 過剰アクセスと短時間スポットアクセスの監視

参加者向けアプリケーションへの同一IPからのアクセスは、60秒の移動時間窓で600リクエストまで許可する。超過時はHTTP 429を返し、参加者へ次の趣旨のメッセージを表示する。

> アクセスが集中しています。少し時間をおいて再度お試しください。

学校、商業施設、イベント会場等の共有Wi-Fiを過度に巻き込まない値とし、管理画面やCSS・JavaScript・画像等の静的ファイルはこの参加者向け制限の主対象にしない。

IPアドレスはアプリの秘密鍵を使ったHMAC-SHA256で識別値へ変換し、平文または復元可能な形式で保存しない。秘密鍵を使わない単純なSHA-256も、IPアドレスを推測照合されやすいため使用しない。操作ログへ生のIPアドレスを記録しない。

リクエスト単位の制限記録は本体SQLite DBへ書き込まず、ロック競合を増やさない専用の一時ストレージへ保存する。記録には失効時刻を持たせ、直近60秒の判定に不要となったデータを定期的またはアクセス時に削除できるようにする。短時間スポットアクセスの判定記録も同じ一時ストレージへ置き、5分の判定と重複警告抑制に不要になった時点で削除する。保存先はWebから直接取得できない場所とし、本番データやバックアップへ含めない。

同一参加者が5分以内に10か所以上の異なるスポットへアクセスした場合は、不正と断定せず警告ログを残す。警告には次を含める。

- 参加者ID
- 判定日時
- 判定対象の開始・終了日時
- 異なるスポットへのアクセス数
- HMAC-SHA256化したIP識別値

Cookieトークン、平文IPアドレス、スポットURL、QRの平文トークンは記録しない。同一参加者について警告後5分間は同条件の重複警告を抑制する。この警告だけでスタンプ取得、参加、応募を禁止・無効化しない。

### 負荷試験用データ

負荷試験は通常の開発用DBとは異なる専用の一時SQLite DBを生成して行う。生成処理は `development` または `test` 環境専用とし、通常セットアップや本番環境から実行できないようにする。試験データと結果を本番DB、通常の開発用DB、本番バックアップへ混入させない。

投入規模はスポット20件、参加者2,000人、スタンプ取得履歴最大40,000件とし、次を測定する。

- 参加者のスタンプ一覧
- スタンプ取得
- 管理画面の集計
- 全参加者CSV
- 応募者CSV
- SQLite DBファイルサイズ
- 同時スタンプ取得時の成功・重複・失敗件数
- SQLiteロック発生数
- 応答時間

使用した条件、データ件数、実行日時、各測定結果を再確認可能な機械可読形式またはMarkdownへ保存する。試験前後に通常の開発用DBのファイルハッシュ等を比較し、変更されていないことを確認する。

## 6. 状態と業務ルール

### イベント状態

優先順位は次のとおり。

1. `is_paused = true`: 一時停止
2. 現在日時が `starts_at` より前: 開催前
3. 現在日時が `ends_at` より後: 終了
4. それ以外: 開催中

スタンプ取得を許可するのは開催中だけとする。終了後もスタンプ一覧と応募情報の確認は可能だが、新規取得は拒否する。

### 達成判定

- 有効・停止を問わず、その参加者が実際に取得した件数を数える
- 取得数が `required_stamp_count` 以上なら達成
- 達成した最初の時点だけ `completed_at` を設定する
- 達成条件を後から下げた場合も、次の画面表示時に達成を反映する
- 達成条件を上げる操作は既達成者への影響を警告し、開催開始後は原則として行わないよう案内する

### スポット停止・削除

- 停止スポットの新規取得は拒否する
- 停止前の取得は達成数へ残す
- 取得履歴のあるスポットは削除不可
- 取得履歴のないスポットは開催前に限り削除可能
- 達成可否の判定でいう「スポット数」は、新規参加者が取得可能な有効スポット数を指す。停止中スポットは数えない
- 削除前に `削除後の取得可能スポット数 < required_stamp_count` となるかをサーバー側で判定する
- 上記に該当する場合、削除確認画面へ「削除するとスポット数が達成必要数を下回り、新規参加者が達成できなくなる」ことと、削除後にイベント設定の見直しが必要であることを表示する
- 警告対象でも削除自体は禁止しない。通常の削除確認を経て管理者が実行できる
- 削除実行時にも同じ条件をトランザクション内で再判定し、確認画面表示後にスポット数や達成必要数が変わった場合も正しい状態を記録する
- 削除後に `取得可能スポット数 < required_stamp_count` の状態なら、スポット管理と管理ダッシュボードへ達成条件の見直しを促す警告を継続表示する
- イベント設定で達成必要数を現在のスポット数以下へ変更するか、スポットを追加して条件が解消された時点で警告を消す

### 応募

- 達成者だけが応募できる
- 参加者1人につき応募1件
- 使用・必須項目は応募時点のイベント設定でサーバー側検証する
- 管理者は `application_deadline_at` を任意に設定できる。NULLの場合は `ends_at` を実効応募締切とする
- 応募設定とイベント設定のどちらを保存する場合も、明示的な `application_deadline_at` があれば `ends_at <= application_deadline_at` をサーバー側で検証する。NULLの場合は `ends_at` が実効応募締切になるため、この追加検証は不要とする
- 応募設定画面では、応募締切入力欄の近くにイベント終了日時を併記する。狭い画面では縦並びでよい
- イベント終了後でも実効応募締切までは、達成済み参加者が新規応募または同じCookieから既存応募を編集できる
- 実効応募締切後は応募内容の閲覧だけを許可し、新規応募と編集を拒否する
- 応募を編集しても `application_number` は変更しない
- 管理者も通常画面から応募内容を改変しない
- 管理者が入力した `privacy_purpose_text` を応募画面へ表示する
- 「個人情報の取り扱いに同意する」チェックを必須とし、クライアント側とサーバー側の両方で検証する
- 同意した日時を `privacy_accepted_at` へ保存する
- MVPではプライバシーポリシー本文、外部URL、同意対象ポリシーの版を登録する機能を持たない
- MVPでは抽選機能と抽選対象確定操作を持たず、応募編集を禁止する条件は実効応募締切後だけとする
- 応募設定を途中で変える場合、既存応募へ遡って新しい必須項目を要求しない

### イベント終了日時と応募締切の整合性

明示的な応募締切より後のイベント終了日時が入力された場合は、イベント設定を保存しない。応募締切を自動的に空欄へ変更したり延長したりせず、画面上部へ共通エラー通知を表示し、終了日時欄の近くへ次の形式の具体的なエラーを表示する。

> 終了日時は、設定済みの応募締切（2026年8月20日 18:00）以前にしてください。先に応募設定で締切を変更することもできます。

エラー後も入力したほかの内容をフォームへ保持する。保存処理はトランザクション等で一体として扱い、不正な保存時にイベント設定や応募設定を部分更新しない。既存の応募内容と応募番号も変更しない。この整合性検証のためのDB項目は追加しない。

イベント設定画面では、終了日時入力欄の近くへ現在の応募締切を参考表示する。

- 明示的な応募締切がある場合: `設定済みの応募締切：2026年8月20日 18:00`
- 応募締切がNULLの場合: `応募締切はイベント終了日時と同じになります`

管理者は、イベント終了日時を応募締切以前にする、応募設定で締切を延長する、または応募締切を空欄にしてイベント終了日時を実効締切にする、のいずれかを明示的に選ぶ。日時の比較と表示はアプリに設定された同一のタイムゾーンへ揃える。

### 応募に関するMVP後の検討

プライバシーポリシー機能を追加する場合は、本文の管理画面登録、外部ページURL、応募画面から全文または外部ページを確認する導線、同意した版・内容の記録、ポリシー変更後の既存応募者の同意の扱いをまとめて設計する。

アプリ内抽選機能を追加する場合は、抽選対象の確定操作、確定日時と実行管理者、確定後の応募編集禁止、確定後に設定や応募内容を変更する場合の扱い、抽選のやり直し制限、除外・当選結果・監査ログ、個人情報の取り扱いと保存期間をまとめて設計する。

### CSV出力

管理画面の「参加・応募集計」から次の2種類を個別に出力する。

#### 全参加者CSV

- ファイル名は `qr-rally-participants.csv`
- イベントへ参加した全参加者を出力する
- ニックネーム、取得数、参加日時（`first_seen_at`）、最終アクセス日時（`last_seen_at`）、達成日時（`completed_at`）を含める
- 応募済みの場合は、応募番号、現在有効な応募項目、応募日時（`submitted_at`）、更新日時（`updated_at`）も含める
- 未応募者の応募関連列は空欄とし、参加状況・達成状況の確認と集計に使用する

#### 応募者CSV

- ファイル名は `qr-rally-applications.csv`
- 応募を完了した参加者だけを出力し、未応募者は含めない
- 応募番号、ニックネーム、取得数、達成日時、現在有効な応募項目、応募日時、更新日時を含める
- 応募者が0人の場合も、現在の設定に対応するヘッダー行だけの正常なCSVを返す
- 抽選や当選者への連絡に使用する。アプリ内抽選機能はMVPへ追加しない

#### 共通条件

- 管理者認証を必須とする
- 現在無効な応募項目の列は出力しない
- UTF-8 BOMを付け、一般的な表計算ソフトで日本語を確認できるようにする
- 文字列が数式として解釈されないよう、CSV数式インジェクション対策を全出力値へ適用する
- 個人情報を含むため、キャッシュ禁止と安全なダウンロード用レスポンスヘッダーを付ける
- 全参加者CSVのダウンロードは `participants_csv_exported`、応募者CSVは `applications_csv_exported` として操作ログへ記録する
- 応募者CSVは `participants` と `applications` の既存データを絞り込んで出力し、DB項目を追加しない

### イベント初期化

- 管理者パスワードの再入力と確認文の入力を要求する
- イベント、応募項目、スポット、参加者、取得、応募、イベント関連ログを削除する
- 管理者、復旧キー、アプリ設定、製品・スキーマバージョンは残す
- 処理開始前にバックアップのダウンロードを案内する
- 完了後は初期設定画面へ移動する

## 7. URLとリクエストの原則

実際のURL形式はWebサーバー互換性を確認して決める。ルーティング書換えへ依存しすぎず、サブディレクトリ設置でも動かす。

- スポット取得URLにはスポットの平文トークンだけを含める
- 参加者トークンをURLへ含めない
- 変更処理はPOSTとし、GETアクセスだけで設定変更や削除を行わない
- POST後はリダイレクトし、ブラウザ再読込による再送信を防ぐ
- 管理画面は認証とCSRF検証を必須とする
- 参加者の応募にもCSRF検証を行う
- CSV、QR、バックアップのダウンロード時は権限とレスポンスヘッダーを検証する

### CSRF検証失敗時の419応答

CSRFトークンが無効または期限切れの場合は、対象データを一切保存せずHTTP 419を返す。同じ通常ブラウザの別タブで管理者ログインに成功すると、同じPHPセッションに保存されたCSRFトークンが更新されるため、それ以前に開いていた参加者フォームのトークンは無効になる。この拒否はCSRF対策として正常な動作とする。

参加者向けフォームでは専用の419画面を使用し、次を表示する。

- 入力を続けられないこと
- 別画面でのログイン等により、画面の有効期限が切れた可能性があること
- 入力内容は送信・保存されていないこと
- イベント入口を開き直して、もう一度入力すること
- 対象イベントの「イベント入口へ戻る」リンク

参加者向け419画面には「管理者ログインへ戻る」を表示しない。419応答を生成する際は、対象イベントの入口URL等、参加者用テンプレートに必要な情報を必ず渡す。不足したテンプレート変数によって500エラーやPHP警告へ変化させてはならない。

管理者向けフォームでは、従来どおり管理者向けレイアウトと管理者ログインへの案内を表示する。少なくとも、初回参加・ニックネーム登録、応募内容の確認、応募内容の送信、応募設定の保存、およびその他の管理画面のCSRF保護対象操作へ適用する。今後追加する参加者向けフォームも、管理者向け419画面を流用せず、その参加者が戻れる入口を表示する。

管理者へログインした後に参加者入口を新しく開いた場合は最新のCSRFトークンを使用するため、通常どおり送信できる。別ブラウザやプライベートウィンドウはPHPセッションが分かれるため、この同一セッション内の期限切れ事象の再現対象外とする。

## 8. 入力検証と上限

具体的な文字数は画面設計時に確定し、DB、サーバー側検証、HTMLの上限を一致させる。少なくとも次を設ける。

### フォームエラー表示の共通方針

複数の入力項目を持つフォームでバリデーションエラーが発生した場合は、各入力項目付近の具体的な赤いエラーメッセージに加え、共通テンプレートを使ってフォーム上部へ次の通知を目立つ形で表示する。

> 入力内容にエラーがあります。各項目の赤いメッセージを確認してください。

送信後に画面上部が表示された場合でも、画面下部等にある個別エラーの存在へ気付けるようにする。少なくとも次を対象とし、今後追加する複数項目フォームにも同じ共通テンプレートを適用する。

- イベント設定
- スポット追加・編集
- 応募設定
- 初回参加
- 参加者の応募・応募編集

ログイン失敗やパスワード再設定等、具体的なエラー理由をすでに画面上部へ単独表示するフォームでは、同じ内容の共通通知を重ねて表示しない。

### 項目別の入力検証

- イベント名とスポット名はそれぞれ50文字以内とし、管理画面の入力属性とサーバー側バリデーションの両方へ同じ上限を適用する
- 文字数はマルチバイト文字を正しく1文字として数える
- 既存のイベント名またはスポット名が50文字を超える場合も、自動切り詰めや一括更新は行わない。該当データを次回編集・保存するときにサーバー側で拒否し、50文字以内への短縮を求める
- ニックネーム、説明、案内文の文字数上限
- 開始日時が終了日時より前であること
- 達成数が1以上かつ登録スポット数以下であること
- メールアドレスの形式と確認入力の一致
- 電話番号・住所は文字列として扱い、数値変換しない
- 応募設定・イベント設定の双方で、明示的な応募締切がイベント終了日時と同じか、それより後であること。逆転する場合は保存を拒否し、日本語のエラーを表示する
- 全参加者CSVと応募者CSVの全出力値でCSV数式インジェクションを防ぐ処理
- HTMLへ表示するすべての利用者入力のエスケープ

スポット印刷用HTMLと全スポットPDFでは、イベント名・スポット名を固定幅からはみ出さないよう適切に折り返す。各スポットの掲示物がQRコードや注意書きと重ならずA4一枚へ収まることをレイアウト条件とする。イベント入口用印刷画面は複数ページを許容する。

## 9. バックアップ・復元の実装条件

詳しい利用者操作はTODOの「バックアップからの復旧イメージ」を正本とする。実装では次を満たす。

- 専用形式はマニフェストとSQLite DBファイルから構成する
- マニフェストへ製品、形式バージョン、生成日時、テーブル別件数、ファイルハッシュを記録する
- CSVエクスポートを復旧用データとして扱わない
- 稼働中DBのバックアップは単純なファイルコピーではなく、SQLiteのオンラインバックアップ機能等で整合性を確保する
- アップロード後、作業用DBとして展開し、`integrity_check`、スキーマ、件数、外部キー、バージョンを検査する
- 作業用DBの検査中は現行DBを変更しない
- 現行DBを閉じ、同じファイルシステム上で退避とリネームを行う短い切り替え処理にする
- 失敗時は現行DBを維持し、作業用DBを安全に破棄できる
- 完了・失敗・期限切れの一時ファイルを削除する
- 復旧中の画面を閉じても、再ログイン後に状態または失敗理由を確認できる

## 10. セキュリティの最低条件

- パスワードは `password_hash()` と `password_verify()` を使用
- 管理者セッションIDをログイン成功時と権限変更時に再生成
- CookieはHTTPS前提で `Secure`、`HttpOnly`、`SameSite=Lax`
- CSRFトークンをセッションに結び付ける
- DBアクセスはPDOのプリペアドステートメントを使用
- ログイン失敗と参加者向け過剰アクセスへ時間窓付きの制限を設ける
- IPアドレスを保存する場合はアプリ秘密鍵によるHMAC-SHA256へ変換し、用途と保持期間を明記する
- エラー画面へSQL、パス、秘密情報を表示しない
- ZIP展開時にパストラバーサル、シンボリックリンク、想定外ファイルを拒否
- バックアップをWeb公開領域へ常設しない
- 個人情報を含むCSVとバックアップへキャッシュ禁止ヘッダーを付ける

### パスワードと復旧キーを両方紛失した場合

再インストールやバックアップ復元ではなく、SSHでサーバーへ接続できる所有者だけがCLI専用コマンドを実行する。

```text
php bin/reset-admin-credentials.php
```

コマンドは次の条件を満たす。

- `PHP_SAPI === 'cli'` 以外では即座に拒否する
- スクリプトを公開URLから直接実行できない場所へ置く
- パスワードをコマンド引数で受け取らず、標準入力から確認を含めて対話入力する
- 可能な環境では入力中のパスワードを画面へ表示しない
- パスワード強度を通常の管理者作成時と同じ規則で検証する
- 新しい復旧キーを安全な乱数で生成し、平文は実行時に一度だけ表示する
- 新しいパスワードと復旧キーは `password_hash()` で保存する
- 管理者メールアドレスは確認表示し、必要な場合だけ対話入力で変更できる
- DBトランザクション内で認証情報と `auth_version` を更新する
- 成功時に既存の管理者セッションをすべて無効化する
- `admin_credentials_reset_via_cli` を操作ログへ記録するが、秘密情報は記録しない
- 失敗時は管理者情報を変更せず、一般利用者が理解できるエラーを標準エラーへ出す

SSHおよびSQLite DBを含むファイルへのアクセス権を持つ人は、技術的にはアプリの全データを操作できる。このCLIは新しい権限を与えるものではなく、サーバー所有者がDBを手作業で編集せず安全に復旧するための経路と位置付ける。

バックアップから復元すると、バックアップ取得時点の管理者認証情報も戻る。復元後にそのパスワードと復旧キーが不明な場合は、同じCLIをもう一度実行して現在の認証情報を再発行する。

## 11. 実装順序

実装は [QRデジタルスタンプラリー 実装手順書](qr-stamp-rally-implementation-plan.md) に従う。

最初から配布ZIPやブラウザインストーラーを作らない。ローカル専用のセットアップ処理でSQLite DBと開発用管理者を用意し、管理者・参加者の主要機能を完成・検証した後に、確定したDBスキーマと設定方法をブラウザインストーラーで包む。

大きな順序は次のとおり。

1. ローカル開発基盤とSQLiteスキーマ
2. 管理者機能
3. 参加者機能
4. 応募、集計、CSV、QR、印刷
5. ローカルでMVP全体を通し確認
6. セキュリティ、負荷、障害試験
7. バックアップと復元
8. 環境診断とブラウザインストーラー
9. XServer実機設置
10. ZIP配布物、マニュアル、デモ

通常機能とスキーマが固まるまでは、インストーラー、復元形式、配布ZIPを完成扱いにしない。

## 12. 受け入れ条件

実装完了は、TODOのチェックだけでなく少なくとも次を満たした状態とする。

- DB作成操作や接続情報入力なしに、ブラウザ操作だけでSQLiteへインストールできる
- 管理者パスワードと復旧キーの平文がDB・ログへ残らない
- パスワードと復旧キーを両方失っても、CLIからイベントデータを維持したまま認証情報を再発行できる
- CLI再設定後に、それ以前の管理者セッションがすべて無効になる
- 20スポットを登録して個別QRと印刷用データを出力できる
- イベント名とスポット名が管理画面・サーバー側の両方で50文字以内に制限される
- 50文字を超える既存名は自動変更されず、該当データの次回編集・保存時に短縮を求められる
- イベント名が印刷用HTMLとPDFの左右で欠けず、スポット名・注意書き・QRコードが重ならない
- スポット個別印刷と全スポットPDFが1スポットにつきA4一枚へ収まる
- イベント入口案内が長文の場合は、内容を欠落させず複数ページへ自然に続く
- スポット個別印刷画面、全スポット印刷画面、全スポットPDFに平文のスポット取得URLが表示されない
- イベント入口用印刷画面には平文の入口URLが表示され、管理者向けQR確認画面は従来どおり確認できる
- 個別QRのSVGを現在の表示順、日本語スポット名、ASCII代替名を含む仕様どおりのファイル名で取得できる
- スポット並び替え後の再ダウンロードで新しい表示順がファイル名へ反映される
- QR再発行後に古いURLが無効になり、新しいURLだけが有効になる
- QR再発行後もスポット情報と過去の取得実績が変化しない
- QR確認画面と最終確認ダイアログの両方で、配布済みQRの交換を警告する
- スポット削除後のスポット数が達成必要数を下回る場合、削除前に新規参加者が達成不能になることを警告する
- 警告対象のスポットを削除すると、スポット管理と管理ダッシュボードに達成条件見直しの警告が表示される
- 達成必要数の変更またはスポット追加で条件を解消すると、削除後警告が消える
- 初回参加、重複取得、停止スポット、期間外取得が仕様どおり動く
- 初回参加フォーム直前、参加者向け諸注意、各スポットのQR掲示物、イベント入口用案内、参加者向け取扱説明書のすべてにブラウザ利用上の注意が掲載される
- iPhone向けに標準カメラとSafariを案内し、コントロールセンターのコードスキャナーを使わないよう表示する
- 初回参加フォーム直前のiPhone向け警告が、指定された文面で独立した目立つ枠として常時表示される
- Android向けに標準カメラと普段使用するChrome等の通常ブラウザを案内する
- アプリ内ブラウザ、一時的なブラウザ、プライベートブラウズでは履歴が失われる場合があると表示する
- Cookieを失った参加者の履歴を復旧・統合する機能や参加者向け復旧キーがMVPに含まれない
- `tools/cookie-probe/` がGitで管理され、本番配布ZIPには含まれない
- 同時に同じQRへアクセスしても取得履歴が重複しない
- 指定数到達時だけ達成状態となる
- 応募項目の有効・必須設定が画面とサーバー側の両方へ反映される
- 個人情報の利用目的に規定の初期値が入り、管理者が変更できる
- 対象となる複数項目フォームの入力エラー時に、個別エラーと指定文面の画面上部通知が同時に表示される
- 具体的なエラー理由を画面上部へ単独表示するフォームでは、同内容の共通通知が重複しない
- 応募締切入力欄の近くにイベント終了日時が表示される
- 応募締切が空欄ならイベント終了日時が実効締切になる
- イベント終了日時より前の応募締切はサーバー側で拒否され、日本語のエラーが表示される
- イベント設定画面の終了日時付近に、設定済み応募締切または実効締切の説明が表示される
- 明示的な応募締切以前および同じイベント終了日時は保存でき、それより後の終了日時はサーバー側で拒否される
- 終了日時の拒否時に画面上部の共通通知と項目付近の具体的なエラーが表示され、ほかの入力内容が保持される
- 応募締切が空欄の場合は、ほかの日時条件を満たす任意のイベント終了日時へ変更できる
- 保存拒否時にイベント設定、応募締切、既存の応募内容、応募番号が変更されず、応募締切も自動変更されない
- 日時の比較と表示が設定されたタイムゾーンで一致する
- イベント終了後でも別途設定した応募締切までは達成済み参加者が応募・編集でき、締切後は閲覧だけできる
- 応募編集後も応募番号が変わらない
- 個人情報の利用目的と同意欄が表示され、未同意の応募がサーバー側で拒否され、同意日時が保存される
- プライバシーポリシー本文・外部URL・抽選対象確定の機能がMVPに含まれない
- 全参加者CSVに未応募者を含む全参加者が出力され、応募済み参加者には応募情報も出力される
- 応募者CSVに応募済み参加者だけが出力され、応募者0人でもヘッダー行だけのCSVを取得できる
- 現在無効な応募項目が両CSVへ出力されない
- 両CSVをUTF-8 BOM付きで取得でき、日本語と個人情報項目が文字化けしない
- 数式として解釈され得る値が両CSVで安全に出力される
- 両CSVを管理者だけが取得でき、キャッシュ禁止等の安全なヘッダーが付く
- 全参加者CSVと応募者CSVのダウンロードが区別して操作ログへ記録される
- イベント初期化で管理者とアプリ設定を残し、イベントデータだけ削除できる
- 2,000人・最大40,000取得履歴のデータで主要画面とCSV出力を確認できる
- バックアップを空DBへ復元できる
- 復元を意図的に失敗させても既存データが変化しない
- サブディレクトリ設置を保証対象にする場合、そのURLでQR取得と管理画面が動く
