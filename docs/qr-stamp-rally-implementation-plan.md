# QRデジタルスタンプラリー 実装手順書

作成日: 2026-08-10

## 1. この手順書の目的

管理者・参加者機能をローカルで完成させてから、バックアップ、ブラウザインストーラー、XServer設置、ZIP配布へ進むための作業順序を定める。

利用者目線の要件は [QRデジタルスタンプラリーTODO](../todos/qr-stamp-rally.md)、技術仕様は [実装仕様書](qr-stamp-rally-implementation-spec.md) を正本とする。この文書には要件を再掲せず、実装の順番、各段階の成果物、次へ進む条件だけを記載する。

## 2. 基本方針

- 最初からインストーラー形式では開発しない
- ローカル開発中は専用のセットアップ処理でSQLite DBを生成する
- 画面と業務処理が固まるまで配布ZIPの構成を確定しない
- 管理者機能と参加者機能を実際のブラウザで通してから設置機能へ進む
- 各フェーズの終了時に自動テスト、手動確認、コミットを行う
- 後のインストーラーでも使えるよう、DB作成処理自体は画面から分離する
- MVP後の候補は先回りして実装しない

## 3. ローカル開発時の起動方法

開発中はブラウザインストーラーを使わず、次の役割を持つ開発用コマンドを用意する。

- 設定ファイルのひな型を作る
- 開発用SQLite DBを新規作成する
- マイグレーションを実行する
- 開発用管理者を作る
- 必要に応じてサンプルイベントとスポットを投入する
- DBを初期化してやり直せる

コマンド名は実装開始時に決めるが、例えば次のような責務に分ける。

```text
php bin/setup-local.php
php bin/migrate.php
php bin/seed-demo.php
php bin/reset-local.php
```

ローカルではMacBook Pro上で既に稼働しているApacheの80番ポートを使用する。LAN内からアクセスできるアドレスを、開発用ベースURLとして明示する。

```text
APP_ENV=development
APP_BASE_URL=http://192.168.11.5/
```

HTTPの標準ポート80を使うため、URLへ `:80` は付けない。Apacheのサブディレクトリへ配置する場合は、`http://192.168.11.5/qr-rally/` のように配置先のパスまで含める。

開発環境のHTTPでは参加者Cookieの `Secure` を無効にし、本番HTTPSでは必ず有効にする。詳細エラー、デモデータ投入、DB初期化コマンドは本番環境で無効にする。

- アプリケーションのディレクトリ構成
- Composerと依存ライブラリの固定
- 設定読込と `development`／`production` の切り替え
- SQLite接続、WAL、外部キー、`busy_timeout`
- マイグレーションの仕組み
- ローカルセットアップ・リセット用コマンド
- 共通のHTTPレスポンス、テンプレート、エラー処理
- 最小限のテスト実行環境

### 確認すること

- 新しいローカル環境でDBを作り直せる
- マイグレーションを複数回実行しても壊れない
- DBファイルと設定がWebから直接取得できない
- ルート直下の開発URLでトップページを表示できる

### 完了条件

空の画面だけでも、設定読込、DB接続、テストが安定して動くこと。

## 5. フェーズ1: 管理者の基本機能

### 実装するもの

- 開発用管理者の作成
- ログイン、ログアウト、セッション更新
- パスワードハッシュ
- CSRF対策
- 管理者復旧キーとパスワード再設定
- CLI専用の管理者認証緊急再設定
- `auth_version` による既存セッションの一括無効化
- 管理画面の共通レイアウト
- 複数項目フォームで使う、個別エラーと画面上部のエラー概要の共通テンプレート
- CSRF検証失敗時に保存せずHTTP 419を返す共通処理と、参加者用・管理者用の別々の419画面
- イベント基本設定
- イベント名の管理画面・サーバー側50文字制限
- イベント終了日時と明示的な応募締切の双方向整合性検証
- 終了日時付近への設定済み応募締切または実効締切の参考表示
- 一時停止と開催状態の算出
- 操作ログの基礎

### 確認すること

- 正しい認証情報だけでログインできる
- セッション固定、CSRF、連続ログイン失敗への対策が動く
- 管理者向けCSRF検証失敗では、管理者向けレイアウトと管理者ログインへの案内を含むHTTP 419が返る
- パスワードと復旧キーの平文がDB・ログへ残らない
- パスワードと復旧キーの両方を失った状態から、CLIでデータを消さずに復旧できる
- CLI再設定前のログイン済みセッションが使用できなくなる
- 開催前、開催中、終了、一時停止が日時と設定から正しく決まる
- イベント設定の入力エラー時に、個別エラーと指定文面の画面上部通知が表示される
- 50文字のイベント名を保存でき、51文字以上は保存できない
- 50文字を超える既存イベント名は自動変更されず、次回編集・保存時に短縮を求められる
- 明示的な応募締切以前および同じ終了日時は保存でき、それより後の終了日時は保存できない
- 終了日時の保存拒否後も入力値と既存データが保持され、応募締切が自動変更されない
- 応募締切が空欄なら、通常の日時条件を満たす任意の終了日時へ変更できる
- 日時の比較と表示が設定されたタイムゾーンで一致する

### 完了条件

ローカルで管理者がログインし、イベントの基本情報を保存・確認できること。

## 6. フェーズ2: スポット管理とQR

### 実装するもの

- スポット追加、編集、並び替え、停止、条件付き削除
- 管理画面メニュー、ページ見出し、操作手順の「スポット管理」表記
- スポット名の管理画面・サーバー側50文字制限
- 削除後のスポット数が達成必要数を下回る場合の削除前警告
- 削除後に達成条件の見直しを促す管理画面警告
- スポット用UUID v4の生成とハッシュ保存
- 個別QRのSVG表示・ダウンロード
- 現在の表示順と日本語スポット名を使ったSVGファイル名
- UTF-8ファイル名とASCII代替名を併記するダウンロードヘッダー
- QRに含めるURLの生成
- 古いQRを無効化するQR再発行
- QR確認画面の常時警告と再発行時の最終確認ダイアログ
- 管理画面からQRを読み取る実機確認用ページ

### 確認すること

- 内部数値IDがQRやURLへ出ない
- QRをスマートフォンで読み、設定したLAN内URLへ到達できる
- サブディレクトリを含むベースURLでも正しいURLになる
- `01-中央図書館-qr.svg` のような日本語名でダウンロードできる
- ファイル名禁止文字、制御文字、空になる名称を安全に処理できる
- 日本語ファイル名非対応環境向けの `spot-01-qr.svg` がヘッダーに含まれる
- 並び替え後のファイル名に現在の表示順が反映される
- 削除後のスポット数が達成必要数を下回る場合、確認画面に新規参加者が達成不能になる旨が表示される
- 警告を確認して削除した後も、スポット管理と管理ダッシュボードに達成条件見直しの警告が残る
- 達成必要数を下げるかスポットを追加して条件を解消すると警告が消える
- QRトークンを再発行すると古いQRが無効になる
- 再発行してもスポット情報と取得実績が変化しない
- QR確認画面と最終確認ダイアログの両方に交換警告が表示される
- 50文字のスポット名を保存でき、51文字以上は保存できない
- 50文字を超える既存スポット名は自動変更されず、そのスポットの次回編集・保存時に短縮を求められる

### 完了条件

管理者がスポットを登録し、画面に出たQRをスマートフォンで読み取れること。

## 7. フェーズ3: 参加者のスタンプ取得

### 実装するもの

- 初回参加とニックネーム登録
- 参加者UUID v4のCookie保存とDB側ハッシュ
- スポット取得
- 重複取得防止の一意制約
- 期間外、一時停止、停止スポットの拒否
- スタンプ一覧と取得済み表示
- 達成数と達成日時
- Cookie・機種変更等の諸注意
- 初回参加フォーム直前に常時表示する、独立した目立つiPhone向け警告枠
- 標準カメラと同じ通常ブラウザの継続利用を案内する参加者向け諸注意
- iPhoneのコードスキャナー、アプリ内ブラウザ、一時ブラウザ、プライベートブラウズに関する注意
- 履歴の復旧・統合を行わず、参加者向け復旧キーを設けないMVPの扱い
- 初回参加フォームのCSRF検証失敗時に、イベント入口へ戻れる参加者専用の419案内

### 確認すること

- QRから初回参加、取得、一覧へ自然に進める
- 同じQRを再読込しても取得件数が増えない
- 同時リクエストでも重複行ができない
- 期間外等の拒否を画面だけでなくサーバー側でも行う
- 取得済みスポットを停止しても過去の達成数が減らない
- 初回参加フォーム直前に、確定したiPhone向け警告文が独立した目立つ枠として常時表示される
- 参加後の諸注意画面からも、端末別のブラウザ案内を確認できる
- 実機確認ではiPhoneの標準カメラからSafari、Androidの標準カメラから通常ブラウザで複数スポットを取得し、同じ履歴が継続する
- コードスキャナーを技術的に判別する処理や、参加者向け復旧キーが追加されていない
- 初回参加フォームのCSRFトークンが無効でも500エラーにならず、データを保存せずHTTP 419と「イベント入口へ戻る」リンクが表示される

### 完了条件

管理者が作った複数のQRを参加者がスマートフォンで巡り、指定数で達成できること。

## 8. フェーズ4: 応募と管理集計

### 実装するもの

- 応募機能の有効・無効
- 氏名、メール、住所、電話番号の使用・必須設定
- 任意の応募締切日時と、空欄時にイベント終了日時を使う実効締切判定
- 応募締切入力欄付近へのイベント終了日時の表示
- 応募設定保存時にも維持する `イベント終了日時 <= 応募締切日時` の検証
- 個人情報利用目的の表示、必須同意、`privacy_accepted_at` の保存
- 個人情報利用目的の初期値と管理者による変更
- 応募入力、確認、完了、締切前編集
- 応募確認・送信時のCSRF検証失敗に対する、参加者専用の419案内
- 応募番号
- 参加数、スポット別取得数、達成数、応募数
- 全参加者CSV `qr-rally-participants.csv`
- 応募者だけに絞った応募者CSV `qr-rally-applications.csv`
- 両CSVのUTF-8 BOM、動的な応募項目列、安全なダウンロードヘッダー
- 両CSVへのCSV数式インジェクション対策
- CSVの種類を区別する操作ログ

### 確認すること

- 未達成者は応募できない
- 同じ参加者の応募は1件だけ
- 応募編集後も応募番号が変わらない
- 応募締切を空欄にするとイベント終了日時が使われる
- 応募締切入力欄の近くにイベント終了日時が表示され、狭い画面でも確認できる
- イベント終了日時と同じ日時または終了後の日時を応募締切に設定できる
- イベント終了日時より前の応募締切はサーバー側で拒否され、日本語のエラーが表示される
- 不整合の拒否によってイベント設定、応募締切、応募内容、応募番号が部分更新されない
- イベント終了後でも応募締切までは達成済み参加者が新規応募・編集できる
- 応募締切後は内容を閲覧できるが、新規応募・編集はできない
- 個人情報の利用目的が表示され、未同意はクライアント側・サーバー側の両方で拒否される
- 個人情報の利用目的の初期値が「抽選と当選者への連絡のために使用します。」となり、管理者が変更できる
- 同意日時が `privacy_accepted_at` へ保存される
- 応募確認・送信のCSRFトークンが無効な場合は応募内容を保存せず、HTTP 419とイベント入口への案内が表示される
- 管理者の通常画面から応募内容を編集できない
- プライバシーポリシー本文・外部URL・抽選対象確定の機能が追加されていない
- 全参加者CSVには未応募者を含む全参加者と、応募済みの場合の応募情報が出力される
- 応募者CSVには応募済み参加者だけが出力される
- 応募者が0人でも応募者CSVをヘッダー行だけで取得できる
- 応募設定で無効にした項目が両CSVへ出力されない
- 両CSVの日本語と個人情報項目を一般的な表計算ソフトで文字化けなく確認できる
- 数式として解釈され得る値が両CSVで安全に出力される
- 両CSVを管理者だけが取得でき、キャッシュ禁止等のヘッダーが付く
- 両CSVのダウンロードが種類を区別して操作ログへ記録される
- 応募者CSVのためにDB項目が追加されていない

### 完了条件

参加から達成、応募、管理者の集計、全参加者CSV・応募者CSV取得まで一連の操作が完了すること。

### MVP後へ送るもの

- プライバシーポリシー本文または外部URLの登録、確認導線、同意した版の記録、ポリシー変更後の再同意
- アプリ内抽選、抽選対象確定、確定後の応募編集ロック、やり直し・除外・当選結果・監査ログ・個人情報保存期間

## 9. ローカルMVP確認ゲート

ここまでを最初の大きな区切りとする。次の項目が通るまでブラウザインストーラーへ進まない。

- [ ] 管理者の主要操作を一通り実行できる
- [ ] スマートフォンで参加から達成まで確認できる
- [ ] イベント設定、スポット追加・編集、応募設定、初回参加、参加者の応募・応募編集で、個別エラーと画面上部の共通通知を確認できる
- [ ] ログイン失敗やパスワード再設定で、同内容の共通通知が重複表示されない
- [ ] 応募あり・なしの両方を確認できる
- [ ] 開催前、開催中、一時停止、終了を確認できる
- [ ] スポット停止とイベント初期化のルールを確認できる
- [ ] 主要な入力エラーが日本語で分かる
- [ ] 自動テストと手動テストの既知の失敗がない

この時点では、ローカルセットアップコマンドでDBを作成できればよく、一般利用者向けインストーラーは不要。

## 10. フェーズ5: QR印刷とPDF

### 実装するもの

- 個別QRの印刷用HTML
- 全スポットの印刷用HTML
- 日本語フォントを使ったA4 PDF
- イベント入口用・各スポット用の案内文
- QR掲示物へ載せる標準カメラ・通常ブラウザ利用の短い注意文
- スポット印刷物から平文のスポット取得URLを除外し、取得用QRは維持
- イベント入口用印刷画面での平文入口URLの表示
- スポット印刷物の1スポットA4一枚レイアウトと、入口案内の自然な複数ページ対応

### 確認すること

- 日本語イベント名とスポット名が文字化けしない
- イベント名が左右で欠けず、スポット名とQRコード、注意書きとQRコードが重ならない
- スポット個別印刷と全スポットPDFが1スポットにつきA4一枚へ収まる
- イベント入口案内は長文でも内容が欠けず、必要に応じて複数ページへ自然に続く
- スポット個別印刷画面、全スポット印刷画面、全スポットPDFに平文のスポット取得URLが表示されない
- イベント入口用印刷画面には平文の入口URLが表示される
- 管理者向けQR確認画面のURL確認機能が変わっていない
- 実際に印刷したQRを複数端末で読み取れる
- QR掲示物、イベント入口用案内、参加前警告、諸注意、参加者向け取扱説明書でブラウザ案内の内容が一致している
- PDF生成に失敗しても印刷用HTMLを使用できる

## 11. フェーズ6: セキュリティ・負荷・障害試験

### 実施すること

- 認証、CSRF、XSS、SQLインジェクションのテスト
- 同一ブラウザの別タブで管理者ログインした際に、先に開いていた参加者フォームが安全に期限切れとなることの実機確認
- Cookie属性とセッション期限の確認
- `tools/cookie-probe/` による有効期限付きCookieとセッションCookieのA・B別QR実機確認
- 検証端末、OSバージョン、読み取り方法、画面を閉じたか、サーバー判定をMarkdownへ記録
- 緊急認証再設定コマンドがWeb経由の実行を拒否することの確認
- CLIへ渡したパスワードと復旧キーが引数、画面、ログへ不要に残らないことの確認
- CLI実行前の全管理者セッションが無効になることの確認
- URL・トークンの推測困難性の確認
- 参加者向けアプリケーションを対象とした、同一IP・60秒間600リクエストの過剰アクセス制限
- アプリ秘密鍵によるIPアドレスのHMAC-SHA256化と、期限付き一時ストレージの削除処理
- 5分以内に10か所以上へアクセスした参加者の警告ログと、警告後5分間の重複抑制
- `busy_timeout=5000ms` と、100ms・250msの最大2回に限定したSQLiteロック再試行
- HTTP 429・503の日本語案内と、安全なQR再読み取り
- 通常の開発用DBとは別の一時SQLite DBへ、20スポット、2,000人、最大40,000取得履歴を投入する開発・試験専用処理
- スタンプ一覧・取得、管理集計、全参加者CSV、応募者CSV、DBサイズ、同時取得結果、ロック数、応答時間の測定
- 試験条件と結果を再確認可能な形式で保存し、通常DBが変更されていないことをハッシュ等で確認

### 確認すること

- 同一IPから60秒間に600リクエストまでは許可され、超過時はHTTP 429と日本語案内が返る
- 管理画面や静的ファイルが参加者向けIP制限の主対象になっていない
- IPアドレスが平文でDB、一時ストレージ、操作ログへ保存されない
- 共有Wi-Fiの複数参加者を過度に巻き込む厳しい制限になっていない
- 同一参加者が5分以内に10か所以上へアクセスすると、取得を禁止せず必要項目を含む警告ログが残る
- 同一参加者の警告後5分間は重複警告が抑制され、Cookieトークン・平文IP・スポットURLが記録されない
- SQLiteロック時に100ms、250msの最大2回だけ再試行し、回数・待機時間・最終失敗をテストできる
- 再試行後も失敗した場合はHTTP 503とQRの再読み取り案内が表示される
- 一意制約違反は再試行せず取得済みになり、タイムアウト後の再読み取りでも重複取得が発生しない
- 20スポット、2,000人、最大40,000取得履歴を専用の一時DBへ投入できる
- 負荷試験前後で通常の開発用DBが変更されず、本番環境から試験処理を実行できない
- 指定された測定項目と試験条件を再確認可能な形式で保存できる

### 同一ブラウザの別タブによるCSRF期限切れ確認

1. 同じ通常ブラウザのタブAで、未参加状態の参加者入口を開く
2. ニックネーム入力画面を表示したままにする
3. タブBで管理者ログインを成功させ、CSRFトークンを更新する
4. タブAへ戻り、古い参加フォームを送信する
5. HTTP 419が返ることを確認する
6. 500エラーやPHP警告が表示されないことを確認する
7. 参加者データが登録されていないことを確認する
8. 「入力内容は送信されていません」と表示されることを確認する
9. 「イベント入口へ戻る」リンクが表示されることを確認する
10. イベント入口を開き直して入力し、正常に参加登録できることを確認する

管理者ログイン後に参加者入口を新しく開いた場合は、最新のCSRFトークンで通常どおり登録できることも確認する。別ブラウザやプライベートウィンドウはセッションが分かれるため、この手順の再現対象外とする。

### SQLite採用の確認ゲート

- [ ] XServer実機相当の条件でデータ破損がない
- [ ] 集中時の失敗率と待ち時間が実運用可能
- [ ] HTTP 429・503の後に安全に再試行できる
- [ ] 一意制約により重複取得が発生しない

ここを満たせない場合に限り、MySQLへの変更を検討する。SQLiteとMySQLの両対応にはしない。

### 実施すること

- XServerスタンダードへファイルを配置
- `public_html`外にDB・設定・ログを置く構成を確認
- PHP 8.3、拡張、権限、SQLite WALを確認
- インストーラーを最初から通す
- スマートフォンで実際のHTTPS QRを読む
- QR、PDF、CSV、バックアップ、復元を確認
- フェーズ6の負荷・同時取得試験を、XServerスタンダード上の隔離された検証環境で再実行
- XServer固有のエラーと解決方法を記録

### XServer実機での負荷試験

通常運用中のイベントDBや本番公開中の環境へ負荷試験データを投入してはならない。XServer上に次の条件を満たす専用の検証環境を用意する。

- 本番イベントとは異なるSQLite DBを使用し、負荷試験専用の一時SQLite DBを生成する
- `development` または試験専用環境として実行する
- 通常の参加者がアクセスできないURLまたは非公開領域で実施する
- 負荷試験コマンドをWeb経由で実行できないようにする
- 試験後に一時DBと不要な結果ファイルを削除できるようにする
- 本番用DB、設定、ログ、バックアップへ試験データを混入させない

データ規模はフェーズ6と同じく、スポット20件、参加者2,000人、スタンプ取得履歴最大40,000件、負荷測定に必要な件数の応募者とする。2,000人の同時接続は必須とせず、最大想定データを投入した状態で少人数の同時スタンプ取得ワーカーを実行する。

少なくとも次を測定し、試験条件と数値を後から再確認できるJSONおよびMarkdown等で保存する。

- テストデータ投入時間
- 参加者のスタンプ一覧表示相当の処理時間
- スタンプ取得処理時間
- 管理画面の集計処理時間とスポット別集計時間
- 全参加者CSVと応募者CSVの生成時間
- SQLite DBのファイルサイズ
- 同時スタンプ取得の成功件数、取得済み件数、失敗件数
- SQLiteロックの発生回数と再試行回数
- HTTP 429・503の発生状況
- 試験終了後の取得履歴件数
- `PRAGMA integrity_check` の結果
- PHPバージョン
- XServerの契約プラン、サーバー番号またはサーバー環境を識別できる情報
- 実行日時

### 同時取得と再試行の実機確認

同じ参加者・同じスポットへ複数リクエストを同時に送り、次を確認する。

- 新規取得は1件だけになり、残りは「取得済み」として扱われる
- 取得履歴が重複しない
- 一意制約違反をSQLiteロックとして再試行しない
- SQLiteロック時の再試行が100ms、250msの最大2回で止まる
- 最終失敗時はHTTP 503とQR再読み取り案内が返る
- HTTP 503またはタイムアウト後に同じQRを読み直しても、重複取得が発生しない

必要な場合は試験専用の一時DBだけを対象に、短時間のSQLiteロックを意図的に発生させる。本番運用中のDBをロックしてはならない。

### XServer実機でのSQLite採用ゲート

試験後、次を確認してSQLiteの継続採用を判定する。

- `PRAGMA integrity_check` が `ok` で、外部キー違反がない
- 取得履歴の重複と想定外の失敗がない
- タイムアウト後に安全に再試行できる
- 集計とCSVを実用可能な時間で処理できる
- 同時取得時の失敗率と待ち時間が実運用可能である
- 通常運用DBが試験前後で変更されていない
- XServer上でもWALと `busy_timeout=5000ms` が有効である
- 試験条件と結果が保存されている

すべて満たした場合にSQLite採用を確定する。満たせない場合だけMySQLへの変更を検討し、SQLiteとMySQLの両対応は行わない。

### 完了条件

- XServer実機でフェーズ6相当の負荷・同時取得試験を実行した
- 試験条件と結果を保存した
- SQLite採用ゲートの各項目を判定した
- 本番用DBへ試験データが混入していない
- 一時DBと不要な試験用ファイルの後始末を確認した
- SQLiteを継続採用するか、再検討が必要かを記録した
