# QRデジタルスタンプラリー 実装手順書

作成日: 2026-08-10

## 1. この手順書の目的

管理者・参加者機能をローカルで完成させてから、バックアップ、ブラウザインストーラー、XServer設置、ZIP配布へ進むための作業順序を定める。

利用者目線の要件は [QRデジタルスタンプラリーTODO](../todos/qr-stamp-rally.md)、技術仕様は [実装仕様書](qr-stamp-rally-implementation-spec.md) を正本とする。この文書には要件を再掲せず、実装の順番、各段階の成果物、次へ進む条件だけを記載する。

## 2. 基本方針

- 最初からインストーラー形式では開発しない
- ローカル開発中は専用のセットアップ処理でSQLite DBを生成する
- 画面と業務処理が固まるまで配布ZIPの構成を確定しない
- 管理者機能と参加者機能を実際のブラウザで通してから設置機能へ進む
- 各フェーズの終了時に自動テスト、手動確認、コミットを行う
- 後のインストーラーでも使えるよう、DB作成処理自体は画面から分離する
- MVP後の候補は先回りして実装しない

## 3. ローカル開発時の起動方法

開発中はブラウザインストーラーを使わず、次の役割を持つ開発用コマンドを用意する。

- 設定ファイルのひな型を作る
- 開発用SQLite DBを新規作成する
- マイグレーションを実行する
- 開発用管理者を作る
- 必要に応じてサンプルイベントとスポットを投入する
- DBを初期化してやり直せる

コマンド名は実装開始時に決めるが、例えば次のような責務に分ける。

```text
php bin/setup-local.php
php bin/migrate.php
php bin/seed-demo.php
php bin/reset-local.php
```

ローカルではMacBook Pro上で既に稼働しているApacheの80番ポートを使用する。LAN内からアクセスできるアドレスを、開発用ベースURLとして明示する。

```text
APP_ENV=development
APP_BASE_URL=http://192.168.11.5/
```

HTTPの標準ポート80を使うため、URLへ `:80` は付けない。Apacheのサブディレクトリへ配置する場合は、`http://192.168.11.5/qr-rally/` のように配置先のパスまで含める。

開発環境のHTTPでは参加者Cookieの `Secure` を無効にし、本番HTTPSでは必ず有効にする。詳細エラー、デモデータ投入、DB初期化コマンドは本番環境で無効にする。

## 4. フェーズ0: 骨組みと開発基盤

### 実装するもの

- アプリケーションのディレクトリ構成
- Composerと依存ライブラリの固定
- 設定読込と `development`／`production` の切り替え
- SQLite接続、WAL、外部キー、`busy_timeout`
- マイグレーションの仕組み
- ローカルセットアップ・リセット用コマンド
- 共通のHTTPレスポンス、テンプレート、エラー処理
- 最小限のテスト実行環境

### 確認すること

- 新しいローカル環境でDBを作り直せる
- マイグレーションを複数回実行しても壊れない
- DBファイルと設定がWebから直接取得できない
- ルート直下の開発URLでトップページを表示できる

### 完了条件

空の画面だけでも、設定読込、DB接続、テストが安定して動くこと。

## 5. フェーズ1: 管理者の基本機能

### 実装するもの

- 開発用管理者の作成
- ログイン、ログアウト、セッション更新
- パスワードハッシュ
- CSRF対策
- 管理者復旧キーとパスワード再設定
- CLI専用の管理者認証緊急再設定
- `auth_version` による既存セッションの一括無効化
- 管理画面の共通レイアウト
- イベント基本設定
- 一時停止と開催状態の算出
- 操作ログの基礎

### 確認すること

- 正しい認証情報だけでログインできる
- セッション固定、CSRF、連続ログイン失敗への対策が動く
- パスワードと復旧キーの平文がDB・ログへ残らない
- パスワードと復旧キーの両方を失った状態から、CLIでデータを消さずに復旧できる
- CLI再設定前のログイン済みセッションが使用できなくなる
- 開催前、開催中、終了、一時停止が日時と設定から正しく決まる

### 完了条件

ローカルで管理者がログインし、イベントの基本情報を保存・確認できること。

## 6. フェーズ2: スポット管理とQR

### 実装するもの

- スポット追加、編集、並び替え、停止、条件付き削除
- スポット用UUID v4の生成とハッシュ保存
- 個別QRのSVG表示・ダウンロード
- QRに含めるURLの生成
- 管理画面からQRを読み取る実機確認用ページ

### 確認すること

- 内部数値IDがQRやURLへ出ない
- QRをスマートフォンで読み、設定したLAN内URLへ到達できる
- サブディレクトリを含むベースURLでも正しいURLになる
- QRトークンを再発行すると古いQRが無効になる

### 完了条件

管理者がスポットを登録し、画面に出たQRをスマートフォンで読み取れること。

## 7. フェーズ3: 参加者のスタンプ取得

### 実装するもの

- 初回参加とニックネーム登録
- 参加者UUID v4のCookie保存とDB側ハッシュ
- スポット取得
- 重複取得防止の一意制約
- 期間外、一時停止、停止スポットの拒否
- スタンプ一覧と取得済み表示
- 達成数と達成日時
- Cookie・機種変更等の諸注意

### 確認すること

- QRから初回参加、取得、一覧へ自然に進める
- 同じQRを再読込しても取得件数が増えない
- 同時リクエストでも重複行ができない
- 期間外等の拒否を画面だけでなくサーバー側でも行う
- 取得済みスポットを停止しても過去の達成数が減らない

### 完了条件

管理者が作った複数のQRを参加者がスマートフォンで巡り、指定数で達成できること。

## 8. フェーズ4: 応募と管理集計

### 実装するもの

- 応募機能の有効・無効
- 氏名、メール、住所、電話番号の使用・必須設定
- 個人情報利用目的と同意
- 応募入力、確認、完了、締切前編集
- 応募番号
- 参加数、スポット別取得数、達成数、応募数
- 参加・応募CSV
- CSV数式インジェクション対策

### 確認すること

- 未達成者は応募できない
- 同じ参加者の応募は1件だけ
- 応募編集後も応募番号が変わらない
- 締切後は変更できない
- 無効な項目を保存・出力しない
- CSVを一般的な表計算ソフトで確認できる

### 完了条件

参加から達成、応募、管理者の集計・CSV取得まで一連の操作が完了すること。

## 9. ローカルMVP確認ゲート

ここまでを最初の大きな区切りとする。次の項目が通るまでブラウザインストーラーへ進まない。

- [ ] 管理者の主要操作を一通り実行できる
- [ ] スマートフォンで参加から達成まで確認できる
- [ ] 応募あり・なしの両方を確認できる
- [ ] 開催前、開催中、一時停止、終了を確認できる
- [ ] スポット停止とイベント初期化のルールを確認できる
- [ ] 主要な入力エラーが日本語で分かる
- [ ] 自動テストと手動テストの既知の失敗がない

この時点では、ローカルセットアップコマンドでDBを作成できればよく、一般利用者向けインストーラーは不要。

## 10. フェーズ5: QR印刷とPDF

### 実装するもの

- 個別QRの印刷用HTML
- 全スポットの印刷用HTML
- 日本語フォントを使ったA4 PDF
- イベント入口用・各スポット用の案内文

### 確認すること

- 日本語イベント名とスポット名が文字化けしない
- 長い名称でもQRと重ならない
- 実際に印刷したQRを複数端末で読み取れる
- PDF生成に失敗しても印刷用HTMLを使用できる

## 11. フェーズ6: セキュリティ・負荷・障害試験

### 実施すること

- 認証、CSRF、XSS、SQLインジェクションのテスト
- Cookie属性とセッション期限の確認
- 緊急認証再設定コマンドがWeb経由の実行を拒否することの確認
- CLIへ渡したパスワードと復旧キーが引数、画面、ログへ不要に残らないことの確認
- CLI実行前の全管理者セッションが無効になることの確認
- URL・トークンの推測困難性の確認
- 過剰アクセス制限
- 20スポット、2,000人、最大40,000取得履歴のテストデータ投入
- 同時スタンプ取得時のSQLiteロック試験
- `database is locked` 発生時の待機・再試行・画面表示確認
- 集計、CSV、管理画面の応答時間測定

### SQLite採用の確認ゲート

- [ ] XServer実機相当の条件でデータ破損がない
- [ ] 集中時の失敗率と待ち時間が実運用可能
- [ ] タイムアウト後に安全に再試行できる
- [ ] 一意制約により重複取得が発生しない

ここを満たせない場合に限り、MySQLへの変更を検討する。SQLiteとMySQLの両対応にはしない。

## 12. フェーズ7: バックアップ・復元

### 実装するもの

- SQLiteオンラインバックアップ
- マニフェストとDBを含むZIP
- 管理画面からのダウンロード
- バックアップの形式・ハッシュ・整合性検査
- 稼働中環境への安全なDB差し替え
- 新規環境への復元
- 失敗時の現行DB維持と退避DBへの復帰

### 確認すること

- 最大想定データでもPHPの制限時間内に処理できる
- 壊れたZIP、別製品、非対応版を拒否する
- 復元失敗前後で現行DBが変化しない
- 復元後に管理者・参加者画面が動く
- 一時バックアップが期限後に残らない

## 13. フェーズ8: ブラウザインストーラー

この段階で初めて一般利用者向けインストーラーを作る。

### 実装するもの

- PHP 8.3と必須拡張の診断
- HTTPS、書込権限、SQLiteロック動作の診断
- ベースURLの自動候補と手動修正
- DB保存先の決定
- SQLiteスキーマ作成
- 管理者メール、パスワード、復旧キー作成
- 初期設定完了後のインストーラー無効化
- バックアップから復元する設置経路

### 再利用するもの

インストーラー独自のSQLや管理者作成処理は書かず、ローカル開発で使用してきた次を呼び出す。

- 環境診断サービス
- DB作成・マイグレーション処理
- 管理者作成処理
- 設定保存処理
- バックアップ検証・復元処理

### 完了条件

空の配置先で、ブラウザ操作だけにより管理画面へログインできること。インストール済み環境で再実行できないこと。

## 14. フェーズ9: XServer実機設置

### 確認する配置

1. 初期ドメイン直下
2. 初期ドメインのサブディレクトリ

独自ドメインは初期ドメイン直下と同じ構造として扱い、公開前に追加確認する。

### 実施すること

- XServerスタンダードへファイルを配置
- `public_html`外にDB・設定・ログを置く構成を確認
- PHP 8.3、拡張、権限、SQLite WALを確認
- インストーラーを最初から通す
- スマートフォンで実際のHTTPS QRを読む
- QR、PDF、CSV、バックアップ、復元を確認
- XServer固有のエラーと解決方法を記録

## 15. フェーズ10: ZIP配布と公開準備

### 実装・作成するもの

- 本番不要ファイルを除外した配布ZIP
- Composer依存物を含む、サーバー側Composer不要の構成
- バージョン情報とリリースノート
- ファイル改ざん確認用チェックサム
- インストール、初期設定、QR印刷、バックアップ、復元の手順
- よくあるエラーと診断方法
- デモ環境の日次初期化

### 最終確認

- [ ] 新しくダウンロードしたZIPだけで設置できる
- [ ] 開発設定、テストデータ、秘密情報がZIPに含まれない
- [ ] 初見の手順でXServerへ設置できる
- [ ] サブディレクトリでも全URLが正しい
- [ ] DB、バックアップ、ログをWebから直接取得できない
- [ ] アンインストール・個人情報削除方法が分かる

## 16. 実装時のコミット単位

大きな一括実装を避け、原則として次の単位でコミットする。

- 開発基盤
- DBスキーマとマイグレーション
- 管理者認証
- イベント設定
- スポット管理
- 参加者登録
- スタンプ取得
- 達成判定
- 応募
- 集計・CSV
- QR・PDF
- セキュリティ・負荷対策
- バックアップ・復元
- インストーラー
- XServer対応
- 配布物・文書

各コミットでは、その変更に対応するテストを同時に追加する。
