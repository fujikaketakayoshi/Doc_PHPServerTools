## 目的とMVP

商店街、学校、展示会、自治体・地域イベント等が、専用アプリや月額SaaSなしで短期のQRスタンプラリーを開催できるようにする。主催者がスポットを登録し、参加者がQRを読み取ってスタンプを集め、達成状況を確認できるところまでをMVPとする。

## 要件を確定する

- [x] 1イベントあたりの想定スポット数と参加者数を決める
-- 20スポット2000名
- [x] 会員登録なし、ニックネーム、メール登録のどれをMVPにするか決める
-- ニックネーム
- [x] 同一端末・同一ブラウザでの参加識別方法を決める
-- UUID v4を使って問題ない。UUIDを避けるという意味ではなく、連番や日時ベースの推測可能な値を使わないという意味。PHPの安全な乱数からUUID v4を生成し、Cookieへ保存する。
-- Cookieには `Secure`、`HttpOnly`、`SameSite=Lax` を付ける。DBにはUUIDそのものではなくSHA-256等のハッシュを保存し、Cookieが漏れていないDB単独の流出から参加者になりすまされにくくする。
- [x] スタンプ取得条件を決める（QR内トークン、合言葉等）
-- QRコード読み取りでリダイレクトされるURLに到達
- [x] 全達成・指定数達成・コース別達成のうちMVP範囲を決める
-- 指定数達成のみの最大値で全達成もフォロー、コース別などの複雑な条件はつけない
- [x] 不正取得対策の強度と、完全防止は保証しない旨を決める
-- スポットごとにUUIDを紐づけるようにすれば単純なIDがQRコードのURLに露出する場合よりはかなり不正しづらくなる、完全防止できないことには言及しておく
- [x] イベント終了後の保管・削除方針を決める
-- MVPは1インストールにつき1イベントとし、過去イベント一覧、スポット複製、複数イベント管理は作らない。開催終了後も現在のイベントを集計・CSV出力できる状態で保持し、管理者が削除するまでは閲覧できるようにする。
-- 同じ環境で次のイベントを開く場合は「イベントデータを初期化」して、イベント設定とスポットを最初から登録し直す。初期化対象はイベント設定、スポット、参加者、取得履歴、応募、イベント操作ログとし、管理者アカウントとアプリ設定は残す。誤操作に備えて初期化前にバックアップのダウンロードを強く案内するが、実行必須にはしない。

## 主催者向けMVP

- [x] 初期設定と管理者ログイン
-- パスワードの平文保存は行わず、PHPの `password_hash()` で必ずハッシュ化する。DBを見てパスワードを確認できる仕様は、DB漏えい時に管理画面まで即座に乗っ取られるため不可とする。
-- MVPではメールによるリマインダーは作らない。インストール時に一度だけ長い「管理者復旧キー」を発行し、利用者にダウンロードまたは安全な場所への保存を求める。復旧キー自体もDBにはハッシュで保存し、管理画面の再設定ページで「管理者メールアドレス＋復旧キー＋新しいパスワード」を入力すると再設定できるようにする。
-- 管理者復旧キーでの再設定と、データバックアップからの復旧は別機能とする。パスワードを忘れただけならバックアップは使わず、管理画面の再設定ページで復旧キーと新パスワードを入力するだけにする。
-- パスワードと復旧キーの両方を紛失した場合は、再インストールやバックアップ復元を行わない。サーバーへSSH接続できる所有者が、公開ディレクトリ外のCLI専用コマンドを実行し、新しい管理者パスワードと復旧キーを再発行する。既存のイベント・参加者・応募データはそのまま維持する。
-- 緊急再設定では既存の管理者セッションをすべて無効化し、実行日時と緊急再設定が行われた事実を操作ログへ残す。新しいパスワードと復旧キーの平文はログへ残さない。
-- バックアップ復旧は、DB破損、誤削除、別サーバーへの移転に使う。SQLを手作業で流すのではなく、インストーラーまたは管理画面へバックアップファイルをアップロードして復元する機能を用意する。具体的な流れは「バックアップからの復旧イメージ」に記載する。
- [x] イベント名、説明、開催期間、公開状態の設定
-- 「公開状態」という別項目ではなく、通常は開催期間から `開催前・開催中・終了` を自動判定する。それとは別に緊急用の「受付を一時停止」スイッチだけを設ける。一時停止中は期間を変更せず、参加者へ管理者が設定した案内文を表示する。状態の二重管理を避けつつ、悪天候や現地トラブルに対応できる。
-- イベント名は50文字以内とし、管理画面の入力欄とサーバー側の両方で検証する。既存データが50文字を超える場合は自動で切り詰めず、次回のイベント編集・保存時に短縮を求める。
- [x] スポットの登録・編集・並び替え・停止
-- 一度でもスタンプ取得されたスポットは削除不可とし、停止のみ可能にする。停止前の取得実績は保持して達成数にも数える。停止操作時に「現在の有効スポット数」「現在の達成条件」「新規参加者が達成可能か」を表示し、達成条件の見直しを警告する。開催前で取得実績がないスポットだけは削除可能でもよい。
-- スポット削除後のスポット数が達成必要数を下回る場合、削除前の確認画面で「新規参加者が達成できなくなる」ことと、イベント設定の見直しが必要であることを警告する。削除実行後も、管理画面上に達成条件の見直しを促す警告を表示する。
-- スポット名は50文字以内とし、管理画面の入力欄とサーバー側の両方で検証する。既存データが50文字を超える場合は自動で切り詰めず、そのスポットの次回編集・保存時に短縮を求める。
- [x] スポットごとの一意なQRコード生成
-- 表示できる画面があればいいと思う、んで実際にQRコード読み取ったスマホでユーザー画面に遷移するように
-- QR再発行は、URLの漏えい、意図しない共有、誤掲示等により現在のQRを明示的に無効化する場合に使う。再発行すると古いQR URLは直ちに無効になるが、スポット名、説明、表示順、過去の取得実績は維持する。
-- QR確認画面へ、再発行後は古いQRが使えず、印刷・掲示・配布済みのQRをすべて交換する必要がある旨を常時表示する。実行時にも同内容の最終確認ダイアログを表示するが、確認文入力やチェックボックスまでは要求しない。取扱説明書にも交換が必要であることを記載する。
- [x] QRコードの個別・一括ダウンロード
-- 印刷用の意味。一覧画面で個別QRをPNGまたはSVGとしてダウンロードできるようにし、全スポット分はスポット名・QR・短い案内文を載せた印刷用PDFとして一括生成する。ブラウザの印刷用ページも用意すると、PDF生成に失敗した環境の代替になる。MVPでは凝ったポスターデザインではなく、A4へ1スポットずつ印刷できる基本レイアウトでよい。
-- スポット個別印刷画面、全スポット印刷画面、全スポットPDFには、取得用QRだけを表示し、平文のスポット取得URLを表示しない。QRの撮影・共有を完全には防げないが、不要なコピーや手入力による共有を抑える。広く案内するイベント入口URLは入口用印刷画面へ引き続き表示し、管理者向けQR確認画面も変更しない。
-- スポット印刷用HTMLと全スポットPDFは、イベント名・スポット名を適切に折り返し、スポット名・注意書き・QRが重ならず、各スポットをA4一枚へ収める。PDF上部の長い日本語イベント名も左右を欠けさせない。
-- イベント入口用印刷画面は、イベント説明や参加者向け注意事項を切り捨てたり隠したりせず、内容量に応じた複数ページ印刷を許容して次ページへ自然に続ける。
-- 個別SVGのファイル名は `表示順-日本語スポット名-qr.svg` とする。表示順はダウンロード時点の現在値を2桁でゼロ埋めし、日本語名を維持する。ファイル名に使用できない文字と制御文字は `-` へ置換する。HTTPではUTF-8名と `spot-01-qr.svg` 形式のASCII代替名を指定する。
- [x] 参加者向けトップページと注意事項の編集
-- 必要
- [x] 達成条件と達成時メッセージの設定
-- 必要
- [x] 参加数、スポット別取得数、達成数の集計
-- 必要
- [x] 全参加者CSVと応募者CSVを個別に出力する
-- 管理画面の「参加・応募集計」から、全参加者CSV `qr-rally-participants.csv` と応募者CSV `qr-rally-applications.csv` を個別にダウンロードできるようにする。
-- 全参加者CSVには、全参加者のニックネーム、取得数、参加日時、最終アクセス日時、達成日時を出力する。応募済みの場合は応募番号、現在使用中の応募項目、応募日時、更新日時も含め、参加状況・達成状況の確認と集計に使う。
-- 応募者CSVには応募済み参加者だけを出力し、応募番号、ニックネーム、取得数、達成日時、現在使用中の応募項目、応募日時、更新日時を含める。応募者が0人でもヘッダー行だけのCSVを正常にダウンロードでき、抽選や当選連絡にそのまま使えるようにする。
-- 両CSVは管理者専用、UTF-8 BOM付きとし、無効な応募項目を含めない。CSV数式インジェクション対策、キャッシュ禁止等の安全なダウンロードヘッダー、種類を区別した操作ログを適用する。応募者CSVは既存データの絞り込みであり、DB項目は追加しない。
- [x] イベントデータのバックアップと削除
-- MVPではSQLiteのみを使用し、スタンプ画像やスポット画像のアップロード機能は作らない。バックアップ対象は、イベント設定、スポット、参加者、スタンプ取得、応募、管理者、操作ログ等を含むSQLite DBファイルと、製品・データ形式のバージョン情報とする。
-- 稼働中DBを単純コピーせず、SQLiteのオンラインバックアップAPIを使って整合性のある一時DBを作る。検査用情報と一緒にZIPへまとめ、管理者のPCへダウンロードする。サーバー上の一時ファイルはダウンロード後または作成から1時間後に削除する。
-- 復旧は管理画面またはインストーラーからバックアップを指定し、検査済みSQLite DBへ安全に差し替える。通常利用者にSQL操作を求めない。配布時には文章の復旧手順を必ず用意し、実装が安定した段階で短い操作動画も用意する。

## 参加者向けMVP

- [x] QRからスポット取得ページを開く
-- 必須
- [x] 初回参加時に参加トークンを発行する
-- ブラウザクッキーに保存
- [x] 同じスポットの重複取得を防ぐ
-- 「取得済みです」とか表示する
- [x] スタンプ台紙と取得済みスポットを表示する
-- MVPはスポット一覧を台紙として使い、各カードにスポット名と未取得・取得済み状態を表示する。取得済みカードには共通の丸いスタンプ画像またはCSS製のスタンプ印を重ねる。画像変更機能は作らず、標準デザインを1種類だけ同梱する。スポット写真のアップロードもMVPでは必須にしない。
- [x] 未取得・取得済み・開催前・終了後を分かりやすく表示する
-- スポット取得ページにも一覧画面にも開催前終了後とか出すようにしましょう
- [x] 達成時に完了画面と任意の応募フォームを表示する
-- 応募フォームはMVPに含める。管理者が「応募なし／応募あり」を選び、応募ありの場合は氏名、メールアドレス、住所、電話番号を項目ごとに使用・必須・任意から選べるようにする。管理者が入力した「個人情報の利用目的」を応募画面へ表示し、「個人情報の取り扱いに同意する」チェックを必須にする。同意はサーバー側でも検証し、同意日時を `privacy_accepted_at` へ保存する。MVPではプライバシーポリシー本文や外部URLの登録機能は作らない。
-- 「個人情報の利用目的」の初期値は「抽選と当選者への連絡のために使用します。」とし、管理者が運用内容に合わせて変更できるようにする。
-- メール確認は行わない仕様で問題ない。ただしメール形式の検証、前後空白除去、確認入力欄は設ける。応募は参加トークンごとに1回とし、送信後の変更可否を決める。応募番号を画面へ表示し、主催者が問い合わせ時に照合できるようにする。住所は自由入力1欄から始めれば、郵便番号検索等を作らずに済む。
-- 応募締切は任意設定とし、空欄ならイベント終了日時を使う。設定する場合はイベント終了日時と同じか、それより後の日時だけを許可し、終了日時より前ならサーバー側で拒否して日本語のエラーを表示する。イベント終了後でも、別途設定した応募締切までは達成済み参加者が新規応募または編集できる。
-- 応募設定画面では、締切をその場で比較できるよう応募締切入力欄の近くへイベント終了日時を併記する。狭い画面では縦並びでよい。
-- イベント設定の保存時にも、明示的な応募締切がある場合は `イベント終了日時 <= 応募締切日時` をサーバー側で検証する。不整合になる終了日時は保存せず、応募締切の空欄化・自動延長も行わない。画面上部の共通通知と終了日時付近の具体的なエラーを表示し、ほかの入力内容を保持する。
-- イベント設定画面では終了日時欄の近くへ、明示的な締切がある場合は「設定済みの応募締切：日時」、空欄なら「応募締切はイベント終了日時と同じになります」と参考表示する。管理者は終了日時を締切以前にするか、先に応募設定で締切を延長または空欄化して明示的に解消する。
-- 日時の比較と表示は設定されたタイムゾーンへ揃える。保存拒否時はイベント設定や応募設定を部分更新せず、既存の応募内容・応募番号も変更しない。DB項目は追加しない。
-- 送信後も、同じブラウザの参加トークンで応募締切までは内容を変更できる。応募番号は変えず、最終更新日時を記録する。締切後は内容を閲覧できるが、新規応募と編集はできない。管理者も通常の管理画面から応募内容を編集しない。
-- MVPでは抽選機能と「抽選対象確定」操作を実装しないため、編集不可条件は応募締切後のみとする。
- [x] Cookie削除・機種変更時の注意を表示する
-- どこかに注意を表示するリンクを設置して諸注意を告知しましょう
-- 参加情報とスタンプ履歴はブラウザのCookieで識別する。iPhone SE（第3世代）での実機検証では、コントロールセンターの「コードスキャナー」は同じ画面内のリンク移動ではCookieを維持したが、画面を閉じて別のQRを読み取るとCookieを送信しなかった。最初のスポットを取得できても、2か所目では別参加者として扱われるため使用しないよう案内する。
-- 初回参加フォームの直前へ、iPhoneではコードスキャナーの画面を閉じ、標準の「カメラ」アプリでQRを読み直してSafariから参加するよう、独立した目立つ警告枠を常時表示する。コードスキャナーの技術的な判別や、同じ画面内だけで行うCookie確認には依存しない。
-- Androidは標準カメラからChrome等の普段使用する通常ブラウザで開き、イベント中は毎回同じブラウザを使うよう案内する。アプリ内ブラウザ、一時的なブラウザ、プライベートブラウズでは参加履歴が失われる場合があることも表示する。
-- 同趣旨の案内を参加者向け諸注意、各スポットのQR掲示物、イベント入口用案内、参加者向け取扱説明書にも記載する。
-- 参加者向け復旧キーはMVPへ導入しない。Cookie削除、機種変更、別ブラウザの使用、コードスキャナーの利用で履歴を失った場合、MVPでは履歴の復旧・統合はできない仕様とする。
- [x] スマートフォンで通し操作を確認する
-- もちろんテストはします

## セキュリティ・運用

- [x] 複数項目フォームの入力エラーを見落としにくくする
-- 複数の入力項目を持つフォームでバリデーションエラーが発生した場合は、各項目付近の具体的な赤いエラーメッセージに加え、フォーム上部へ「入力内容にエラーがあります。各項目の赤いメッセージを確認してください。」と目立つ形で表示する。送信後に画面上部が表示されても、画面下部等にある個別エラーへ気付けるようにする。
-- イベント設定、スポット追加・編集、応募設定、初回参加、参加者の応募・応募編集、および今後追加する複数項目フォームを対象とする。ログイン失敗やパスワード再設定等、具体的なエラー理由を画面上部へ単独表示するフォームには、同内容の共通通知を重ねない。
- [x] QRトークンを推測困難にする
-- スポットをUUID管理にすればほぼ推測できないでしょう
- [x] 管理画面の全変更操作にCSRF対策を入れる
-- 応募フォームにもCSRF対策を入れる。加えて二重送信防止のため、参加トークン単位の一意制約とPOST後のリダイレクトを使う。
-- CSRFトークンが無効または期限切れの場合はデータを保存せず、HTTP 419を返す。同じブラウザの別タブで管理者ログインした際にセッション内のCSRFトークンが更新され、先に開いていた参加者フォームが期限切れになる場合も同様に扱う。
-- 参加者向け419画面では、入力を続けられないこと、別画面でのログイン等により画面の有効期限が切れた可能性、入力内容が送信・保存されていないこと、イベント入口を開き直して再入力することを案内し、「イベント入口へ戻る」リンクを表示する。「管理者ログインへ戻る」は表示しない。
-- 管理者向けフォームの419画面は、従来どおり管理者向けレイアウトと管理者ログインへの案内を使用する。今後追加する参加者向けフォームにも、管理者向け419画面を流用しない。
- [x] 開催期間外の取得をサーバー側で拒否する
-- 参加者向けに期間外であることも告知
- [x] 管理者操作と重要イベントをログへ残す
-- ログ対象：管理者ログイン成功・失敗、設定変更、開催期間変更、一時停止・再開、スポット追加・編集・停止、達成条件変更、全参加者CSV・応募者CSV・バックアップ出力、全データ初期化、復旧キーによるパスワード変更など。2種類のCSV出力は操作ログ上で区別する。参加者側はスタンプ取得成功・重複・期間外拒否、応募完了を集計可能な形で残す。ただしパスワード、復旧キー、Cookieトークン、応募内容の全文は操作ログへ記録しない。
- [x] 個人情報を収集しない最小モードを用意する
-- 応募フォームを表示しないこともできるようにしましょう
- [x] 大量アクセス、連続取得への基本的な制限を入れ、URL共有は完全防止できないと明記する
-- URL共有への制限って例えばどんなの？
-- 回答: QRのURLを写真やメッセージで共有された場合、GPSや現地の追加情報を使わない限りサーバー側では現地読み取りと区別できない。このためURL共有の完全防止は行わず、推測困難なスポットトークン、同一参加者の同一スポット重複取得禁止、短時間に多数スポットを取得した場合の記録・警告、IP単位の過剰リクエスト制限を基本対策とする。IPだけで参加を禁止すると学校・会場Wi-Fiの利用者全員を巻き込むため、厳しいIP制限はしない。
-- 参加者向けアプリケーションへの同一IPからのアクセスは、直近1分間に600リクエストまで許可する。超過時はHTTP 429と「アクセスが集中しています。少し時間をおいて再度お試しください。」という趣旨の案内を返す。管理画面や静的ファイルは主な制限対象にしない。
-- IPアドレスは平文や単純ハッシュで保存せず、アプリの秘密鍵を使ったHMAC-SHA256識別値に変換する。制限判定用データは本体SQLiteと分離した期限付き一時ストレージへ保存し、直近1分の判定に不要となった記録は削除できる構成とする。操作ログにも生のIPを残さない。
-- 同一参加者が5分以内に10か所以上の異なるスポットへアクセスした場合は、参加者ID、判定日時・時間帯、異なるスポット数、HMAC化したIP識別値を警告ログへ記録する。同じ参加者の重複警告は警告後5分間抑制する。Cookieトークン、平文IP、スポットURLは記録せず、この警告だけで取得や応募を無効化しない。
- [x] バックアップからの復旧を試す
-- バックアップをどう作るかから決めましょう
-- 方針: 上記のダウンロード式バックアップを実装し、別の空DBまたは検証用環境へ復元する。参加者、スタンプ取得、応募、設定、画像が戻ることと、ログインできることをリリース前に確認する。
- [x] 想定規模に近いデータ量で簡易負荷確認を行う
-- これはできなそうなのでぶっつけですかね
-- 提案: 2,000人が同時接続する試験は不要だが、20スポット、参加者2,000人、最大40,000件の取得履歴というテストデータはローカルまたはVPSへ投入できる。一覧、スタンプ取得、集計、CSV出力の応答時間とDBサイズを測る。少人数で同時アクセス試験も行い、少なくとも完全なぶっつけ本番は避ける。実イベントではアクセスが開催時間全体へ分散する想定だが、開始直後と人気スポットへの集中には注意する。
-- 負荷試験では通常の開発用DBを変更せず、開発・試験環境だけで生成できる専用の一時SQLite DBへ、20スポット、2,000人、最大40,000取得履歴を投入する。参加者のスタンプ一覧、スタンプ取得、管理集計、全参加者CSV、応募者CSV、DBサイズ、同時取得時の成功・重複・失敗件数、SQLiteロック発生数、応答時間を測定し、再確認可能な形式で結果を保存する。本番環境や通常セットアップから誤実行できないようにする。
-- SQLiteの `busy_timeout=5000ms` を維持する。書き込みで `database is locked` が発生した場合は100ms待機後と250ms待機後の最大2回だけ再試行し、なお失敗する場合はHTTP 503とQRの再読み取り案内を返す。一意制約違反はロックとして再試行せず「取得済み」として扱い、タイムアウト直前に成功していた場合も再読み取りで重複取得させない。

## バックアップからの復旧イメージ

### バックアップを作る

1. 管理者が「設定・保守 → バックアップ」を開く
2. 現在の製品バージョン、対象イベント、参加者数、応募者数、概算ファイルサイズを確認する
3. 管理者パスワードを再入力して「バックアップを作成」を押す
4. アプリがSQLiteのオンラインバックアップAPIで整合性のある一時DBを作り、一時DBの整合性検査後に専用バックアップファイルを生成する
5. 管理者のPCへダウンロードする
6. サーバー上の一時ファイルは、ダウンロード後または作成から1時間後に削除する

ファイル名の例: `qr-rally-backup_2026-08-09_153000.zip`

初期版は `ext-zip` を必須とし、ZIP直下には `manifest.json` と `database.sqlite` の2ファイルだけを含める。製品識別子は `qr-stamp-rally`、バックアップ形式バージョンは `1` とする。CSVは集計・閲覧用であり、復元には使用しない。

`manifest.json` には次を含める。

- 製品識別子、バックアップ形式バージョン、製品バージョン、DBスキーマバージョン
- 作成日時、DBファイル名、DBファイルのSHA-256ハッシュ
- テーブル別レコード件数
- 確認表示用のバックアップ元ベースURL

ベースURLは移行先へ復元せず、復元先の `config.php` を維持する。バックアップ元と復元先のURLが異なる場合は復元確認画面へ注意を表示する。

`database.sqlite` には次を含める。

- 管理者情報（パスワードと復旧キーはハッシュのみ）
- イベント設定と公開状態
- スポットとQR用トークン
- 参加者とスタンプ取得履歴
- 応募内容
- 操作ログ

MVPではアップロード画像がないため、DB内の管理者情報、イベント、スポット、参加者、取得履歴、応募情報、監査ログ等の全データが対象となる。バックアップには個人情報が含まれるため、安全な場所での保管と不要後の削除を画面で案内する。バックアップ作成は管理者だけが実行でき、現在の管理者パスワードの再入力を必須とし、復旧キーによる確認は認めない。

### 稼働中の管理画面から復旧する

1. 管理者が「バックアップを復元」を開く
2. 管理者パスワードを再入力する
3. PCに保存したバックアップファイルを選ぶ
4. アプリが形式、上限、製品・形式・スキーマの互換性、ハッシュ、SQLite、必須テーブル、件数、外部キーとデータ間の関係を作業用DBで検査する
5. 検査結果、イベント名、作成日時、主要件数、バックアップ元URL、現在のデータが置き換わることを確認画面に表示する
6. 確認文を入力して復元を開始する
7. バックアップ内のSQLite DBを作業用ファイルへ展開し、整合性、テーブル、件数、関連を検査する
8. 検査が成功した場合だけメンテナンス状態にして、現在のDBを退避し、作業用DBへ原子的に差し替える
9. 失敗時は作業用ファイルだけを破棄し、既存DBを維持する
10. 復元後に管理者認証情報、イベント、スポット、参加数、応募数を確認し、現在の管理者セッションを終了する

復元直前には現在データの退避バックアップを自動生成する。ただし同じサーバー上の退避は操作ミスから戻すための一時措置であり、サーバー障害に備える正式なバックアップはPC等の別の場所へ保存する。

復元前に「復元後は、バックアップ作成時点の管理者パスワードで再ログインする必要があります。」という趣旨を表示する。復元後はバックアップ時点の管理者パスワードで再ログインし、不明な場合は既存のCLI専用緊急認証再設定を使用する。復元も管理者だけが実行でき、現在の管理者パスワードの再入力を必須とし、復旧キーによる確認は認めない。

### 新規設置・サーバー移転時に復旧する

1. 新しいサーバーへ同じ版または対応する新しい版のアプリを設置する
2. インストーラーでSQLite DBの保存先と書き込み可否を確認する
3. 「新規インストール」ではなく「バックアップから復元」を選ぶ
4. バックアップファイルをアップロードする
5. 互換性と内容の検査結果を確認して復元する
6. 管理者アカウントでログインし、公開URLやサーバー固有設定を確認する
7. QRコードのURLがドメイン変更の影響を受ける場合は、QRの再印刷が必要であることを表示する

### 安全上の制約

- 復元は管理者だけが実行でき、パスワードの再入力を要求する
- アップロードZIPは100MB以下、展開後のSQLite DBは250MB以下、ZIP内は指定された2ファイルだけとする
- ZIP内のディレクトリ、シンボリックリンク、絶対パス、パストラバーサル、同名ファイルの重複、想定外ファイルを拒否する
- 新しい形式のバックアップを古いアプリへ無理に復元しない
- 上限超過、形式不正、ハッシュ不一致、別製品、非対応バージョンの場合は現行DBを変更せず拒否する
- バックアップ検査中は現在の参加者画面を維持し、SQLite DBファイルを切り替える短時間だけメンテナンス表示にする
-- 疑問：PHPでレンタルサーバだと復元処理中にPHPの設定のタイムアウト（多分30秒とか）に引っかからないかな？そこまで長い時間かからない？データ量次第？
-- [!] SQLite採用により、全行をPHPで再登録する必要はなくなった。想定規模ならDBファイルの展開・検査・差し替えは通常30秒以内に収まると見込むが、XServer実機で最大想定データを使って測定する。検査が時間内に終わらない場合は検査だけを複数リクエストへ分割し、DB切り替え自体は短時間で行う。
- 復元成功・失敗と実行者、日時、対象ファイルの識別情報をログへ残す
- バックアップには応募者の個人情報が含まれるため、管理者へ安全な保管と不要時の削除を案内する

復元処理の識別子、現在の処理状態、開始・更新日時、一時ファイルの保存先、エラー概要、メンテナンス状態、有効期限は、Web公開領域外のDB外専用状態ファイルにも保存する。秘密情報や管理者パスワードは保存せず、処理完了または期限切れ後に安全に削除する。`backup_operations` には最終結果と監査記録を残し、状態ファイルは処理中の制御とDB差し替えをまたぐ状態保持に使用する。これにより、画面を閉じた場合や処理中に再ログインした場合も結果または失敗理由を確認できるようにする。

フェーズ7ではバックアップ作成・検証・復元の共通処理までを実装し、未認証で利用できる復元用Web画面は公開しない。新規環境への復元画面はフェーズ8のインストーラーから共通処理を利用する。

### リリース前に確認する復旧試験

- [x] 参加者、取得履歴、応募を含むバックアップを作成できる
- [x] DBのない新規設置先へSQLiteバックアップを復元できる
- [x] 稼働中DBを以前の状態へ戻せる
- [x] 壊れたファイル、別製品のファイル、非対応バージョンを拒否できる
- [x] 復元途中で失敗しても既存データが壊れない
-- 疑問：失敗するデータを投入して既存データが壊れないことは確認できますか？
-- 確認できる。復元DBは作業用ファイルへ展開して検査し、既存DBを直接上書きしない。途中で失敗した場合は作業用ファイルだけを破棄する。全検査に成功した場合だけ、現在のDBを退避してから同じファイルシステム上の原子的なリネームで切り替える。切り替え失敗時は退避DBへ戻す。
-- テストでは、途中で切れたZIP、壊したJSON、重複キー、存在しないスポットを参照する取得履歴、非対応バージョン、指定件数で意図的に例外を発生させるテスト用処理を用意する。失敗前後で既存データの件数とチェックサムを比較し、管理者ログインと参加者画面も確認する。これにより「エラーになった」だけでなく「既存データが変化していない」ことまで自動テストできる。
- [x] 復元後に管理者ログインと参加者画面が正常に動く
- [x] 復元手順を文章だけで第三者が実行できる
-- 正常系に加え、破損ZIP、不正JSON、ハッシュ不一致、ファイル重複、想定外ファイル、絶対パス、パストラバーサル、シンボリックリンク、別製品、非対応バージョン、壊れたSQLite DB、外部キー不整合、意図的な途中例外を試験する。
-- 失敗前後で現行DBのハッシュと件数が変わらないこと、復元後に旧セッションが無効になること、バックアップ時点の管理者情報でログインできること、参加者・管理画面が表示できること、期限切れ一時ファイルが削除されることを確認する。最大想定データの処理時間はXServer上で測定して保存する。
